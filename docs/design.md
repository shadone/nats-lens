# nats-lens design

nats-lens observes a NATS deployment and answers the questions an operator asks when something goes wrong: what failed, when, on which server, and what else happened at the same time. It is read-only towards NATS.

Status: draft; the owner confirmed the decisions in "Decisions confirmed on 2026-10-26", except three that the owner changed (see "Owner review of proposed decisions, 2026-10-26"): all three are built. The owner confirmed the decisions of the account checks and the batched epoch write on 2026-10-27 (see "Owner review of proposed decisions, 2026-10-27").

## Questions it must answer

These come from real incidents on JetStream clusters in Kubernetes and are the acceptance test for the design.

1. A durable consumer disappeared. When, from which server's view, and which client or event removed it?
2. Clients timed out during a GKE node upgrade. Which servers restarted, when did replicas lose quorum, how long until they caught up?
3. Is any server or stream running out of disk? When will it fill at the current rate?
4. Is any consumer's backlog growing, that is, filling faster than it drains?
5. Do all servers agree on each stream's and consumer's configuration, creation time and peers?
6. Which client connections are slow, stalled or reconnecting, and which service owns them?

## Overview

| Topic | Decision | Why |
| --- | --- | --- |
| Language | Go | nats-server exports typed structs for every monitoring payload (`server.Varz`, `server.Connz`, `server.JSInfo`, ...); jsm.go has open-source checks to reuse; the NATS Go client is the reference client |
| Storage | Embedded DuckDB, plus hourly Parquet files as the durable history | One process, no infrastructure; analytic SQL over snapshots; the database is a cache that can be rebuilt from Parquet |
| Checks | SQL files with a metadata header, run after every snapshot | Easy to read, test and add; an agent can run the same SQL |
| API | Connect (connectrpc.com) with protobuf in this repo | Typed end to end; the API is private between the binary and its own UI |
| UI | React and TypeScript built with Vite, embedded into the Go binary | One deployable; Node only at build time |
| Auth | None in the tool; deploy behind IAP or a similar proxy | An identity-aware proxy already decides who may pass; the tool verifies its signed header for mutes |
| Alerting | Findings exported at `/metrics`, and sent to configured webhook and Slack-compatible channels | Deployments can use Prometheus rules, Cloud Monitoring or direct channels; notification choices are proposed, not yet confirmed |
| Deployment | One replica on GKE with `Recreate` and a PVC, preferring a node without a NATS server pod | DuckDB has one writer |

One process, `natslens run`, collects, captures events, runs the checks, archives, and serves the API and the UI, because DuckDB lets one process hold a database file. It does so for every configured system, each with a database of its own.

## Multiple systems

A system is one NATS deployment with its own system account. The configuration lists systems (`systems`), or describes one (a file without `systems`, which is one system with the id `system_id`, default `default`, in `data_dir` unchanged). `Config.ResolvedSystems()` is the one path to per-system settings; `Config.ForSystem` gives each system the configuration a single-system file would, so the code that runs one system knows nothing of the others.

- **What a system owns.** Its database and archive, its collector with its own connection and server tracker, its event capture and connections, its Kubernetes watcher (own kubeconfig and context), its check engine and its archive export. Log lines carry `system`. Systems share the process, the API, the check definitions (`checks.Set`) and the global settings: interval, timeout, events tuning, checks, listen, IAP, `connz_limit`, `subscriptions_interval`, `subsz_limit`, `shutdown_grace`.
- **Start.** The stores open in parallel, each with its own WAL recovery and rebuild, before the API serves. A store that fails to open fails the start: it cancels the other opens, so a refusal does not wait for another system's rebuild, and the stores already open are closed again. A stop signal during the opens is a clean exit. Each data directory gets `system.json` with the system's id on first open; a directory marked for another id refuses the start, and a directory without the file (a single-system nats-lens's) is adopted. A database in the top-level `data_dir` that no listed system uses is warned about.
- **Start check.** Before any system starts, one pass checks every system: its data directory's marker and every file the command reads: the `nats` credentials, TLS CA, certificate and key and the inventory file always, the kubeconfig only in `run` with events on, since only the watcher reads it. A missing file of an `accounts` entry (its `creds`, TLS CA, certificate or key) refuses no start, as an account that cannot connect does not stop its system; the same pass logs a warning naming the system, the entry, the file's key (such as `accounts[APP].creds` or `accounts[APP].tls.ca`) and its path, once per file that cannot be opened (missing or unreadable), for every entry, whether or not the command dials that account (`micro: false` without capture, or `once`, which never dials again), in `run` and `once` and with event capture on or off (the owner's decision of 2026-10-26). A CA the entry inherits from `nats` is checked as `nats.tls.ca`. Any problem refuses the start with one error that names every broken system, before a database opens.
- **Isolation.** After the start check, a system whose NATS is unreachable, whose connection nats.go closed for good, or whose setup fails (the system account's events connection, the Kubernetes client) skips only its own epochs; the others, the API and readiness go on. A failed setup sets the status to `connection_closed` with the error, is logged as an error, and is tried again with the redial backoff (2 seconds doubling to a minute), so a file that is fixed later is picked up. A system whose store fails while running (reading its known servers, recording its start) still stops the process, as a store that fails to open fails the start.
- **Collection status.** Each system reports `CollectionStatus` (`starting`, `collecting`, `not_connected`, `connection_closed`, the newest connection error, when the state began, the start of the newest stored epoch) through `api.Systems`. The collector connection's handlers feed it, chained after the capture's; a connection closed for good stays `connection_closed` while it is dialled again, until it connects.
- **Checks.** One `checks.Set` serves every system; each engine leaves out its own system's nats-lens connections (`System.ToolingNames()`, `natslens-<id>` by default in a list) and logs the loopback guard once for its system. A union of every system's names would also have hidden another system's connection names in a system, and the provider's tooling flag on connections is per system too.
- **Resources.** DuckDB `memory_limit` is the system's own `duckdb_memory_limit` or its share of the budget; `threads` is `max(2, GOMAXPROCS / number of systems)` per database, so that N databases do not each plan for every core. With more systems than half the CPUs the floor of 2 adds up to more threads than CPUs.
- **Shutdown.** One deadline, `shutdown_grace + events.flush_interval` from the signal, for all systems; they stop in parallel, each in the order of [Shutdown](#shutdown) and with its own last `state.json`; the stores close after the API's shutdown returned, in parallel, by the same bound as the last `state.json`; a close still running then is abandoned and the next start replays the write-ahead log.
- **Commands for one database.** `natslens once` collects every system or the one `-system` names; `natslens sql` and `natslens checks run` read the database of `-system` from `-config`, required when the file lists several systems, or `-data-dir`.
- **Kubernetes.** Two systems in one Kubernetes cluster each run a watcher, so node changes are recorded in both databases.

## Collection

Every `interval` (default 30s) the collector takes one snapshot, called an epoch:

1. Discover servers with `$SYS.REQ.SERVER.PING.STATSZ`.
2. Request from every server, through `$SYS.REQ.SERVER.PING.<X>` with a collect window: VARZ, CONNZ (with subscription counts, and with `auth` for each connection's account, user and user JWT), ROUTEZ, GATEWAYZ, LEAFZ, ACCOUNTZ, JSZ (accounts, streams, consumers, config, raft), HEALTHZ (details), RAFTZ, IPQUEUESZ, and SUBSZ when a subscription collection is due (below). Account statistics come from `$SYS.REQ.ACCOUNT.PING.STATZ`.
3. Keep every server's view. Never collapse to one server: an R1 asset (a KV watcher's ordered consumer) appears only on its host, and disagreement between servers is itself a finding.
4. Write the epoch's rows in one transaction. An epoch with missing servers or endpoints is stored and marked partial; `epoch_endpoints` records the outcome of every request per server.

Expected servers are tracked by name, because a server ID changes on every restart. An epoch expects every name seen within `server_forget_after` (default 1h), every server that answered, and every route peer and JetStream meta peer they report.

Discovery stops early once every expected name has answered; otherwise it waits the full collect window (`timeout`, default 3s). Detail requests stop early once every discovered server ID has answered. Replies are counted per distinct server, never by number.

RAFTZ without a filter returns only the system account's groups (the meta group). Stream and consumer groups are listed under the asset's account, so the collector sends one RAFTZ per JetStream account seen in JSZ, recorded as endpoint `RAFTZ:<account>`. The requests for the accounts of the previous epoch go out with the detail requests; only an account seen for the first time needs a second pass. An account with no streams left is dropped from the requests in the first epoch in which every server answered JSZ without it, so it is never recorded missing. An epoch therefore takes at most three windows, and `timeout` must be under a third of `interval`. RAFTZ names leaders by raft peer ID; `raft_stats.leader_name` resolves the name from the peer IDs reported in the same epoch.

Followers report `num_pending`, `num_waiting` and `push_bound` as 0 or false for a consumer (nats-server 2.15 tracks the backlog, pull requests and interest on the leader only), so follower rows store NULL for them and the view `consumer_leader_stats` holds the leader's row. Account JetStream usage in JSZ is the account total across replicas, not one server's share.

Subscription lists: an epoch asks every server for SUBSZ (`{"subscriptions": true, "limit": subsz_limit}`) when the last epoch that asked it started at least `subscriptions_interval` (default 5m) before this one, less one second, so that epochs whose starts jitter by milliseconds keep a 5-minute cadence at a 30-second interval; a clock stepped back to before the last collection's start makes the next epoch ask at once; `0` turns the lists off. SUBSZ goes out with the detail requests in the same window, so the epoch takes no longer, and is part of the epoch's requests, recorded missing for a server, only in an epoch that asked it. An epoch counts as having asked when it sent the request, answered or not, as an account lookup does. nats-server 2.15 lists each account's local subscriptions (`Sublist.localSubs` without leaf hubs, `monitor.go` `Subsz`): those of its clients and of its own system, JetStream and account clients, not the interest of routes, gateways and leaf nodes, so a client's subscription is listed once, by the server it is connected to, under the connection ID CONNZ gives it. A server's internal clients take their IDs from the same counter as its clients, so an ID that the same epoch's CONNZ of that server lacks is an internal client's (a stream's subjects appear under its leader's JetStream client), or a client CONNZ cut at `connz_limit` or that connected or left between the two requests, or any connection when CONNZ did not answer that server in that epoch. SUBSZ names the global account `$G` (`monitor.go` `newSubDetail`, about line 997), as account STATZ does, while CONNZ leaves a global-account connection's account empty (`monitor.go` `Connz`, about line 463); both are stored as reported, so a subscription joins its connection on (`epoch`, `server_id`, `cid`) only, never on the account. The reply's `total` counts the subscriptions before the limit; the server's `num_subscriptions`, which VARZ and the reply also give, counts route and gateway interest too and is not stored with the list. Which subscriptions a cut list keeps follows the server's walk of its accounts and subject tree, not any order nats-lens asks for. A reply of 10,000 subscriptions is about 1.5 MB in config mode (measured over a route in `TestSubszTenThousandOverARoute`) and, by the field sizes, about 2.3 MB with 56-character account keys and name tags; the server sends it as an internal reply, which `max_payload` does not limit. The collector's inbox has no pending limits of its own, but the server it is connected to closes its connection as a slow consumer when the replies queued for it pass that server's `max_pending` (64 MB by default; `client.go` `queueOutbound`): every server's SUBSZ and CONNZ replies arrive on that one connection within one window, and a single reply larger than `max_pending` closes it at once. So `subsz_limit` is at most 100,000 (a reply of about 15 to 25 MB), and limit times servers times about 250 bytes should stay well under the server's `max_pending`. nats-server builds the detail of every local subscription before it applies the limit, about 0.1 to 0.25 s (95 ms on an idle machine, 210 to 250 ms on a loaded one) and 35 MB per call at 200,000 subscriptions, and the stored rows take about 18 bytes each: about 260 MB a day at 5 servers with 10,000 subscriptions each every 5 minutes.

Micro services: the collector asks the services built on the NATS micro framework in each account listed under `accounts` (unless the account sets `micro: false`), over that account's connection, as `$SRV` requests are answered only inside the service's own account. It sends `$SRV.STATS` every epoch and `$SRV.INFO` on the first epoch, every `subscriptions_interval` by the same rule as SUBSZ (with `0`, only on the first epoch), and in an epoch whose STATS names an instance no INFO described, right after the STATS replies. Nothing else is sent: no `$SRV.PING`, no request to an endpoint. Each request has its own reply subject under one inbox, so a no responders status (the account has no service) is told apart per request. The requests go out from the start of the epoch, alongside discovery and the detail endpoints, and each account's requests end within one collect window. A request waits for the account's known instances, under any label: those that answered one of its last three answered STATS (an instance is forgotten once it missed three in a row). It waits for them until the end of the window, except that once an instance it did not know replies (a restart's new ID, or a new instance) it waits for them only until the later of one second after that reply and half the time from the start of the request to the end of the window, but never later than a quarter of that time (at least the quiet period) before its end, which the INFO the new instance calls for keeps. Then it ends 250 ms after its last reply (instances answer from their own subscriptions as the request arrives, a few milliseconds apart on one server and tens of milliseconds across routes), or at the end of the window. So the micro requests add to an epoch whose other requests end sooner: in a one-server test an epoch of 2 to 3 ms took about 252 ms; a STATS that gets neither a reply nor a no responders status keeps the account's requests for the whole window, and an instance that stopped does so in the three epochs after it stopped (to the cap when a new instance replies). A known instance cut at the cap is still waited for in the next epoch. Measured with a 2-second window on one server: after a scale-down (8 of 10 instances stopped) three epochs took the full 2.0 s, then 252 ms; after a restart the epoch that sees the new ID took 1.25 s (half the window and the quiet period), the next two the full window, then 252 ms (`TestMicroScaleDownCost`, `TestMicroRestartCost`). A rolling deploy that replaces an instance every epoch waits until the cap, half to three quarters of the window, in every epoch that sees a new ID, and the whole window in the epochs between while stopped IDs are still known. An instance never seen whose reply comes more than 250 ms after the others' is missed until it once answers in time. A permissions violation comes back as an asynchronous `-ERR`. The collector flushes after subscribing the inbox and after each publish, so the violation has arrived by then, and reads it from the connection's last error by the subject it names; it also puts a watch in front of the connection's error handler that takes the violations of its own requests (`$SRV.INFO`, `$SRV.STATS`, its reply inboxes, which end in `.srv`, and its account lookup while it is in flight), which catches one that a later error overwrote in the last error, and keeps them from the capture's handler, which would record each as a `collector.subscription_error` event, and from the default handler, which would log it every epoch. A refused inbox sends nothing. A refusal is logged once per account, again when what is refused changes (compared by the publish to `$SRV.INFO` or `$SRV.STATS` or the subscription to a reply inbox, not by the server's text, which names each epoch's inbox), and once when it ends. A refused request is not sent again for 10 minutes per label (`refusedRetry`), since nats-server logs every refused publish as an error: each epoch in between stores it with state `held`, the server's refusal as received in `error`, and `refused_at` and `retry_after` (NULL for the other states), written as Unix microseconds made into TIMESTAMP in SQL. The hold ends when the label's connection changes, as a redial may bring new credentials. So the server the entry's connection is on logs each refusal once per 10 minutes per entry and per request. Each request's outcome (`ok`, `no_responders`, `timeout`, `error`) is stored with the epoch; a failure never fails or marks the epoch partial. Replies are decoded with the framework's own types (`micro.Info`, `micro.Stats`); a reply of another type or without a service name and instance ID is counted as undecodable, and a second reply of one instance is dropped. A STATS endpoint without a subject or queue group takes it from the instance's newest INFO. The account is stored as the servers name it, from `$SYS.REQ.USER.INFO` asked once per connection with the first requests (a refused lookup is asked again after 10 minutes), else under its label. Each entry remembers the account its answers were last kept under: the servers' name, or the entry's label when its lookup is refused. One set of answers is kept per account and epoch: of the entries that name one account, the first whose STATS went out and was not refused or failed, else the first; while an earlier entry of the account is connected and its last STATS was not refused, a later one does not ask. In operator mode an entry whose lookup is refused keeps its label, which is never an account's public key, so it is never matched with another entry of the same account, and both ask and are stored. Which entry asks is decided before the requests: when the asking entry's connection drops during them, the account has no answers in that epoch. 100 instances of 20 endpoints answer STATS in about 335 KB and INFO in about 175 KB, gathered in the 250 ms after the last reply and decoded in about 2 ms (`TestMicroManyInstances`).

Account details: every account that any server's ACCOUNTZ lists is looked up with an ACCOUNTZ request filtered to that account (`$SYS.REQ.SERVER.PING.ACCOUNTZ` with `{"account": <id>}`), in operator and config mode alike, alongside the second RAFTZ pass. All lookups of an epoch share one window from their start, so the epoch takes no longer: each stops at the first reply that holds its account, else when every server has answered or the shared window ends, and an account whose turn comes after the window ends is not asked and stays first in line for the next epoch. An account is looked up at most every 10 minutes, answered or not, and at once when the clock stepped back to before its last lookup; at most 32 accounts are looked up in one epoch, the ones never asked first, then the ones asked longest ago, and at most 8 at a time. The lookup time and name of an account that no server's ACCOUNTZ lists any more are forgotten, but only in an epoch in which every server that answered anything answered ACCOUNTZ: an account loaded only on a server that missed ACCOUNTZ keeps its lookup time. The first reply that holds the account is read: the readable name (the name tag, else the decoded JWT's name; nats-server reports the identifier as the name tag of an account without one, and that names nothing), whether it is the system account, whether the server reports its JWT expired, the number of imports (without the service imports from the system account that nats-server adds to every account: the CONNZ and STATZ pings, the user info request and, in a JetStream account, the JetStream API) and of exports, and from the decoded account JWT (`decoded_jwt`) the issue time, the expiry and the limits: connections, leaf nodes, subscriptions, data, payload, JetStream disk and memory, streams and consumers. The JetStream limits are the ones nats-server enforces: the account-wide limits when the JWT sets account-wide disk or memory, else the tiers. A tier `R<n>` limits single-copy bytes (nats-server checks the tier's replicated usage against its limit times n), so its disk and memory limits are multiplied by n and summed over the tiers, which makes the result comparable with the account's replicated usage in JSZ; the account can use every tier at once, and any tier without a limit makes the result no limit. A tier key other than `R<n>` is never selected by the server and is left out. Streams are summed over the tiers. The consumer limit applies to each stream, and nats-server counts each consumer against the tier of its own replicas, so one stream can hold consumers of every tier: the sum over the tiers is the most one stream can hold. A sum that overflows reads as no limit. These tier sums are the upper bound a clustered server enforces; a standalone server checks a new consumer against the selected tier's limit alone (`consumer.go`, about lines 1155 to 1172), so there the stored consumer limit can be higher than what the server enforces. A stream or consumer limit of 0 is not enforced and reads as -1. nats-server does not enforce the data limit; it is kept as the JWT states it. Each answered lookup is one row of `account_details`; a reader takes the newest row at or before an epoch. The JWT itself is never read into any kept value: the reply's `jwt` field is not decoded, and only the claims above are kept.

Account names: the readable name of an operator-mode account (its JWT name tag) comes from JSZ account details and account STATZ, from the name tag CONNZ gives with each connection, from the name tag of connect and disconnect events, and from the account lookups above. A name, once known, is never replaced by the identifier. Only connect and disconnect events name an account: in API audits and snapshot or restore advisories the client's name tag is the user's. A name from the snapshots (JSZ, STATZ, CONNZ, ACCOUNTZ) replaces one learnt from events; an event fills in a name only for an account that has none.

User JWTs: CONNZ is asked with `auth`, so each connection carries its user JWT; nats-server reports a bearer JWT as empty. The collector reads the expiry (`exp`) from the JWT's claims segment without verifying the signature, since the server verified it when the client connected and nats-lens only displays it, and removes the JWT from the reply as soon as it is applied. `connections.user_jwt` records that a JWT was reported and `connections.jwt_expires` its expiry; a JWT that does not decode keeps `user_jwt` true with a NULL expiry and is logged at debug level with its server, connection ID and account, never its content.

Listener certificates: VARZ reports the expiry of each listener's TLS certificate (`tls_cert_not_after` for the client listener and in the cluster, gateway, leaf node, websocket and MQTT blocks); `server_stats` keeps each, NULL for a listener without TLS, a certificate from a certificate store or a GetCertificate callback (VARZ reports only the first configured certificate), or a server that does not report it.

`raft_stats.wal_error` cannot carry the error text: nats-server 2.15 encodes the Go error value as JSON, which gives `{}` for a plain error (a file error keeps only `Op` and `Path`). A non-null value means the group stopped on a critical write error; the text is in the server log.

`natslens run` retries a failed first connect and skips epochs while the collector connection has no server; the API, the event capture and the Kubernetes watcher keep running, and the first connect after failed attempts is recorded as `collector.reconnected`. `natslens once` fails at once.

## Events

Events are what a snapshot misses: short leader changes, a consumer deleted between two polls, who deleted it. Every event is one row: time, source, kind, type, server, account, stream, consumer, client name, client IP, a short summary and the raw JSON.

### Subjects

The system account connection subscribes to:

- `$SYS.ACCOUNT.*.CONNECT` and `$SYS.ACCOUNT.*.DISCONNECT` (with the reason, including slow consumer);
- `$SYS.SERVER.*.LAMEDUCK`, `$SYS.SERVER.*.SHUTDOWN` and `$SYS.SERVER.*.CLIENT.AUTH.ERR`;
- `$SYS.ACCOUNT.CLIENT.AUTH.ERR`;
- `$JS.EVENT.ADVISORY.>`: the JetStream advisories that concern no account (meta leader elected, server out of storage, server removed, API limit reached) are published in the system account;
- `$SYS.ACCOUNT.*.SERVER.CONNS` only with `events.account_connections`, because every server sends it for every account every 30 seconds.

Each JetStream account listed in `accounts` has its own connection, with its own credentials, subscribed to `$JS.EVENT.ADVISORY.>`, `$JS.EVENT.METRIC.>` and `$SYS.ACCOUNT.CLIENT.AUTH.ERR` (account-scoped authentication errors, sent with auth callout, are published in that account). This covers stream created, updated and deleted, consumer created and deleted (nats-server 2.15 sends no advisory for a consumer update), leader elected, quorum lost, max deliveries, NAK, terminated, pause and sampled acks. The account connection also requests `$SYS.REQ.USER.INFO` to learn the account name the servers use for its user.

Cluster advisories (stream and consumer leader elected, quorum lost) arrive in both the asset's account and the system account with the same payload ID; the capture stores the first copy. An account-scoped authentication error is stored once with the server-wide event of the same failure.

### Attribution

JetStream events from an account connection carry the account name the server reports for the connection's user (`$SYS.REQ.USER.INFO`), the name advisories and connection events use. The configured label stands in until it is known, so events stored before that keep the label. A user refused that request, or refused the subscription to its reply inbox, keeps the label for the rest of the process, with one Info line and no stored event; the request is made at most five times per label per process. On other connections a refused inbox stays an error.

Stream and consumer action advisories do not name a client. The API audit advisory of the same call does (`$JS.EVENT.ADVISORY.API`), so audits are always read. An audit and an action match only when received within 2 seconds of each other, in either order, and an audit older than the previous action on the same asset never matches: an idempotent create sends an audit but no advisory, and must not name its client on a later create by someone else. Audits are stored as events only with `events.api_audit`. An action without a matching audit (an inactive consumer removed by the server) has no client. nats-server 2.15 sends no advisory for a consumer update, only for create.

A server that enters lame duck mode sends a lame duck event and, in tests, no shutdown event when it then exits; a plain stop sends a shutdown event. Lame duck and shutdown payloads have no type string, so `events.type` is null for them.

### Connections and writing

Event capture uses its own system account connection (`<name>-events`), so that a burst of events never delays the replies of an epoch. The account connections of event capture, one per account under `accounts`, also ask the account's micro services for the collector, which owns no connection of its own there; without event capture `natslens run` opens one connection per account that asks (`<name>-<account>`, subscribed to nothing but its reply inboxes) and keeps it as it keeps the event connections, and `natslens once` connects each for its one epoch and records one that does not connect as not connected. In `natslens run`, with or without event capture, an account connection whose first dial fails is logged and dialled again with the redial backoff, its requests recorded as not connected meanwhile, rather than failing the system's setup (the owner's change of 2026-10-26, see "Owner review of proposed decisions, 2026-10-26"). With event capture the failed dial is also recorded as `collector.not_connected` for that connection, so its advisories count as not captured until the redial that opens it records `collector.reconnected`; the subscriptions and micro requests start on that connection. Only the system account's events connection, whose files the start check reads, still fails the setup. The event connections retry a failed first connect instead of stopping the collector. nats.go closes a connection for good after repeated authorization errors; such a connection is dialled again, waiting 2 seconds doubling to a minute. A collector connection without a server for 30 seconds is recorded as `collector.not_connected`, again every 10 minutes.

Short-lived connections that close themselves are collapsed (`events.churn`, on by default): a connect is held for `pair_within` (10s); when its disconnect (same server and client ID) arrives in that time with reason "Client Closed", neither is stored, and one `client.churn` event per client name, client host, account and `window` (1m) counts the pairs, so a loopback CLI's summary is still tooling, for example "jetstream-controller connected and disconnected 28 times in 1 min", with the counts per server in `raw`. A connect not closed in time is stored as it is, so connect events reach the database up to `pair_within` late; a disconnect for any other reason is stored with its connect. `client-004` counts the connects of `client.churn` events, and `client-005` fires for a name with `min_short_connections` (20) of them in 10 minutes. On one development cluster, NACK's controller made about 280 of 411 events in 20 minutes this way.

Events are written in batches, every `events.flush_interval` (1s) or `events.batch_size` (500) events. After a failed write the next attempt waits for the flush ticker, doubling up to 30 seconds. Invalid UTF-8 in an event is replaced, as the driver cannot bind it and one bad client name would otherwise fail every batch.

Sources are `sys` and `jetstream` (NATS), `k8s` (the Kubernetes watcher), `finding` (a finding transition) and `collector` (the collector's own records: gap, started, connection lost and reconnected, not connected, messages dropped). A capture gap (a collector restart) is recorded as `collector.gap`, so that the UI never shows silence as health. User JWTs are removed from `raw`: any key named `jwt`, at any depth.

Events follow the same retention as epochs, by receive time.

### Shutdown

Shutdown is bounded by `shutdown_grace` plus `events.flush_interval` from the signal, and that sum plus a margin to exit is the only figure the stop timeout needs:

- the last epoch write gets `shutdown_grace`;
- in parallel, notification delivery stops scheduling attempts; an in-flight request gets until `shutdown_grace` from the signal before cancellation, leaving its batch pending;
- in parallel the event connections drain together for at most one flush interval, and the last events are written in batches of 500 until the deadline, with a `collector.messages_dropped` event counting any that do not fit;
- an interrupted archive export is waited for until the same deadline;
- the last `state.json` write may take 2 seconds past it;
- the API's shutdown runs in parallel from the signal: it waits 5 seconds for calls, then closes their connections, and returns once every call returned; the store closes after that.

So the stop timeout must exceed `shutdown_grace + events.flush_interval + 2s` or 5 seconds, whichever is longer, plus a margin to exit.

## Storage and archive

### Database

nats-lens pins `duckdb-go v2.20000.0`, embedding DuckDB `v2.0.0`. The dependency choice is proposed, not yet confirmed. The engine includes the [upstream shutdown checkpoint fix](https://github.com/duckdb/duckdb/pull/25771) for index entries buffered during WAL replay.

A subprocess regression checkpoints 1,750 synthetic rows, appends 298, and replays the WAL in another process. That process closes without an explicit checkpoint. A third process commits a DELETE; a fourth reopens, verifies an empty full scan, and checks duplicate rejection. This sequence fails at COMMIT with DuckDB 1.5.6 and passes with 2.0.0, using both the default format and an explicit legacy storage format. It establishes prevention for this sequence. It does not establish a historical cause or protection against all corruption.

The [official driver upgrade notes](https://github.com/duckdb/duckdb-go/tree/v2.20000.0#upgrading-to-duckdb-v2) keep the Go API unchanged. Default static libraries come from `go.duckdb.org`; restricted module proxies must allow that source (ASVS 15.2.4). The app does not use appenders, profiling, custom log storage, or `CREATE TABLE AS` row counts, whose behavior changes in this release.

The [storage compatibility rules](https://duckdb.org/docs/2.0/internals/storage) distinguish backward reading from forward reading. DuckDB 2.0 reads older files. New files default to the 2.0 storage format, which older engines cannot read. Disposable probes verify that 2.0 reads 2,048 rows created by 1.5.6, while 1.5.6 rejects a default 2.0 file. A separate probe verifies that 1.5.6 reads a file created with 2.0's explicit legacy storage setting. Forward compatibility is best effort; the application uses the engine default and does not force the legacy setting. Keep a verified pre-upgrade generation for rollback instead of assuming that an older binary can open every file written by the upgraded binary.

Check and replay queries use the documented `lambda x: expression` syntax because DuckDB 2.0 disables single-arrow lambdas by default. The replay node lookup uses explicit JSON paths to avoid ambiguous precedence in a chained JSON-arrow comparison. Existing client-library and replay tests fail with these fixes removed and pass with them restored. The filter expressions, check thresholds, and expected findings remain unchanged.

The driver binds typed nil Go slices as SQL NULL. Production snapshot writes already convert absent lists to non-nil empty lists; API fixtures use explicit empty lists too. A snapshot regression verifies that absent expected, observed, missing, and error lists remain empty lists in storage.

The explicit checkpoint after migrations remains necessary for startup durability. Neither a successful checkpoint nor an engine upgrade repairs existing index divergence. A synthetic pre-existing failure still produces a real typed fatal error in the containment tests. A separate checksum-invalid synthetic WAL exercises archive recovery because DuckDB 2.0 successfully replays the earlier schema-WAL fixture. Follow the [recovery procedure](operations/database-recovery.md) before replacing an affected database.

The DuckDB file `natslens.duckdb` lives in the system's data directory (`data_dir` for a file without `systems`, `<data_dir>/<id>` by default in a list). Tables follow one pattern:

- identity tables hold one row per thing with the first and last epoch it was seen: `servers`, `accounts`, `streams`, `consumers`, `raft_groups`;
- configuration tables hold one row per server per run of consecutive epochs with the same configuration (`first_epoch`, `last_epoch`, `config_hash`): `stream_config`, `consumer_config`. `config_hash` covers the configuration only; a new creation time also starts a new run, so a recreated asset counts as changed while replicas built at different times show the same hash, and the disagreement views list a creation time apart from the configuration. The first epoch after upgrading to this rule starts new configuration rows for every asset, because the old hashes included `created`; a server that misses that epoch keeps its old hash and shows "config differs" until it answers again. A run ends when the server reports nothing for the asset in an epoch, so it never covers an epoch without a report. Agreement checks read only the rows current at the epoch (`first_epoch <= E AND last_epoch >= E`);
- stats tables hold one row per server per epoch and always carry `epoch` and `server_id`: `server_stats`, `routes`, `gateways`, `leafnodes`, `ipqueues`, `health`, `connections`, `account_stats`, `stream_stats`, `stream_source_stats`, `stream_replicas`, `consumer_stats`, `consumer_replicas`, `raft_stats`. The writer hands the rows of `connections`, `routes`, `gateways`, `leafnodes`, `stream_stats`, `stream_source_stats`, `stream_replicas`, `consumer_stats` and `consumer_replicas` to DuckDB as JSON batches of at most 5,000 rows per statement, the server ID bound as a parameter and times passed as Unix microseconds and made TIMESTAMP in SQL (`make_timestamp`); one INSERT per row took about a third of a millisecond, and a batch of 1,000 leaf nodes takes about 2 ms (`TestLeafnodeWriteTime`). A string with invalid UTF-8 is stored with each invalid byte as U+FFFD, as `json.Marshal` writes it, where one INSERT per row could not bind it and failed the epoch (`TestBatchInvalidUTF8`). The decision to batch routes, gateways and leaf nodes, with this replacement in their strings, is proposed, not yet confirmed;
- `stream_source_stats` (migration 0039) holds one row per configured source per stream, server, and epoch, written in the existing JSON batches. A full SHA-256 of the source configuration identifies it independently of source-list order, including start settings, external prefixes, filters, transforms, and durable consumer. Runtime reports match on the identity fields JSZ exposes; ambiguous matches stay unknown. `reported=false` carries NULL activity, lag, and error fields, including followers. Negative reported activity means never heard; a missing row is not evidence of health. Lag is exact `UBIGINT`, activity exact `BIGINT` nanoseconds, and errors retain API code, identifier, and text. The shared epoch-table policy sweeps, exports, and rebuilds this table; archives before 0039 contain none of these rows. `stream_stats.source_config_known` distinguishes a missing configuration from an observed empty source list, including archives predating 0039 (default false). No API or NATS permission changes are needed. This storage choice is proposed, not yet confirmed.
- `account_details` holds one row per answered ACCOUNTZ lookup, with the `epoch` it was made in and the `server_id` whose reply was read. It is swept and archived by epoch like the stats tables, but an epoch has rows only for the accounts looked up in it.
- `subscriptions` and `subscription_lists` hold the SUBSZ replies (migration 0032), only in the epochs that asked SUBSZ. `subscriptions` has one row per (epoch, server, account, subject, queue, cid): a connection's subscriptions with the same subject and queue are folded, with their count in `subs` and their delivered messages summed in `msgs`; `queue` is NULL for none. `subscription_lists` has one row per server that answered, with `total` and `listed`. Both are swept and archived by epoch; an archive written before 0032 has no files for them and rebuilds with both empty. The writer hands the rows to DuckDB as JSON batches of 5,000 (two lists of 10,000 take about 80 ms in memory), since a list holds up to `subsz_limit` rows per server.
- `micro_requests`, `micro_instances`, `micro_stats` and `micro_endpoints` hold the micro service replies (migration 0033), asked over the account connections. `micro_requests` has one row per epoch, account and request sent (INFO or STATS) with its state, the replies that decoded and the error; `micro_instances` one row per instance per INFO reply with version, description, metadata and its endpoints as JSON; `micro_stats` one row per instance per STATS reply with its version and start; `micro_endpoints` one row per instance and endpoint per STATS reply with the counters, cumulative from the instance's start, the last error and custom stats as JSON, at most 1 KB (more is stored as an object with the size). A value a service did not report is NULL. `micro_endpoint_hours` holds, per hour, account, service and endpoint, the requests, errors and processing time of the endpoint's instances, for the 7-day level of an endpoint's average time: each epoch's write adds the increase of each STATS row over the instance's previous row within the hour before to the epoch's hour (`ON CONFLICT` on its unique index); rows are paired by endpoint name and subject, as one instance may have two endpoints of one name in two groups, whose increases are summed into the hour of the name, and by name alone when either row has no subject (a STATS without it before INFO filled it in); two endpoints of one name that both lack a subject are taken as one, which the micro framework never sends; a counter that fell or a new start counts whole, and an instance's first row counts its value only when it started after the previous epoch, so a new instance whose first reply comes later loses what it did before that reply. An instance stored twice in an epoch counts once. The writer passes times as Unix microseconds and makes them TIMESTAMP in SQL (`make_timestamp`), so that the session time zone never shifts an hour. An hour's rows change only while its epochs are written, so the hour's final export holds them whole; the table is archived by hour and swept with the hours wholly before the retention window. At 7 days of 100 instances of 20 endpoints the median of hourly averages reads in 1 ms from it against 159 ms from `micro_endpoints` (2 ms with 50 services), and adding one epoch's sums takes about 20 ms (`TestMicroSizeAtScale` with `MICRO_SIZE_DAYS=7`); `micro_endpoints` takes about 9 bytes a row on disk. They carry `account`, not `server_id`, and are swept and archived by epoch like the stats tables; an archive written before 0033 has no files for them and rebuilds with them empty. The writer hands endpoint rows to DuckDB as JSON batches of 5,000; 100 instances of 20 endpoints (2,000 endpoint rows, 100 rows each in `micro_instances` and `micro_stats`) add about 40 ms to an epoch's write in memory (`TestMicroManyInstances` in the store).
- `client_app_hours` holds, per hour, account, application and loopback, the messages and bytes the application's connections sent and received (migration 0034), for the Applications page's 24 hours of traffic. The application is the connection name before the first "@", `(unnamed)` for a connection without a name or with nothing before the "@"; nats-lens's own connection names have no "@", so they are applications of their own. `loopback` keeps the connections from 127.0.0.1 or ::1 apart, so a reader leaves them out as tooling by the epoch's loopback decision. Each epoch's write adds, in its transaction, the increase of each connection's `in_msgs`, `out_msgs`, `in_bytes` and `out_bytes` over its newest row within the hour before to the epoch's hour (`ON CONFLICT` on its unique index). A connection is (`server_id`, `cid`, `start_time`): a server gives a cid once per process, and the start time tells a restarted server's reuse of one apart. When any counter fell under the same key, the row counts whole; a connection's first row counts its values only when it started after the previous epoch started, so a system seen for the first time, or a connection first listed after a cut list left it out, adds no history. A row that adds nothing (an uncounted first row) does not count in `epochs`, so an hour with no measured connection has no row and reads unset. Rows more than an hour apart do not pair, and an increase over a gap within the hour goes whole to the later row's hour. Traffic is lost in two ways: a connection that closed between two collections loses what it did after its last row, and a server whose list was cut at `connz_limit` adds only its listed connections. A connection stored twice in an epoch counts once. Times are passed as Unix microseconds and made TIMESTAMP in SQL. The table is archived by hour and swept with the hours wholly before the retention window, through the list of hourly tables it shares with `micro_endpoint_hours`; an archive written before 0034 has no files for it and rebuilds with it empty. With 4,096 connections of 512 applications on 3 servers every 30 seconds, adding one epoch's sums takes 15 to 40 ms of an epoch write of 2 to 4.5 s (mostly the connection rows), and the 24 hours of 500 applications in two accounts read in 1 to 3 ms from 14 days of rows (`TestClientAppHoursSize` with `APP_HOURS_SIZE=1` and `=24`, on a laptop).
The other tables are `epochs`, `epoch_endpoints`, `events`, `findings`, `finding_transitions`, `check_runs`, `mutes`, `acknowledgements`, `inventory`, `archive_hours` and `migrations`, and the view `consumer_leader_stats`.

Unique indexes cover `epoch_endpoints`, `server_stats`, `health`, `account_details`, `subscription_lists`, `micro_requests`, `micro_endpoint_hours`, `client_app_hours` and the two configuration tables. The per-entity stats tables have none: the writer keeps one row per entity, server and epoch, and an index there would cost memory and insert time every epoch.

`server_stats` carries the VARZ connection limits (`max_payload`, `max_pending`, `write_deadline_ns`, `ping_interval_ns`, `max_pings_out`) since migration 0025, nullable: rows without VARZ, and rows rebuilt from hours archived before the migration, have NULL limits.

Migrations 0029 and 0030 correct the comments of some of these columns instead of editing 0027 and 0028. Migration 0028 adds nullable columns to two archived tables: `server_stats` the listener certificates' expiry (`tls_cert_not_after`, `cluster_tls_cert_not_after`, `gateway_tls_cert_not_after`, `leafnode_tls_cert_not_after`, `websocket_tls_cert_not_after`, `mqtt_tls_cert_not_after`), and `connections` `user_jwt` and `jwt_expires`. Rows written before it, and rows rebuilt from hours archived before it, have NULL there. Neither table, nor `account_details`, holds a JWT.

Migrations are numbered SQL files, applied once each. Never edit an applied migration; add a new one. The `migrations` table stores each file's SHA-256 and start fails on a mismatch.

Retention is 14 days in DuckDB by default (`retention`), for epochs and events.

DuckDB's `memory_limit` is set at open: `duckdb_memory_limit`, or 60% of the cgroup memory limit, or 1 GiB. DuckDB's own default is 80% of the node's memory, not the pod's.

`natslens sql` runs a query against a database file that no collector holds.

### Archive

The archive is a directory of hourly Parquet files, reached through a `Destination` interface (stage, put, list, fetch); a bucket destination is left for later.

- Each table's rows for an hour go to `archive_dir/<table>/date=YYYY-MM-DD/hour=HH.<export>.parquet`. Events are filed by receive time, epoch tables by the epoch's start time. Identity and configuration rows are exported in every hour their epoch range overlaps, as they are at export time; a rebuild keeps the copy with the highest `last_epoch`. `inventory` is not archived.
- An hour closes when it ended two intervals ago, two event flush intervals ago, and at least a minute ago. Only hours wholly inside the database retention are exported, because the sweep may already have removed part of an older hour.
- `archive_hours` records each exported hour with its epoch and event counts. A closed hour whose counts change later (an event written late) is exported again. The open hour is exported provisionally every `archive_provisional_every` (5m) and finally once closed. Recovery reaches the latest successful manifested export; disabled, failed or delayed exports can leave a larger gap. Missed hours are caught up after downtime.
- Each export of an hour writes files named by its export id (the export's start time), then the manifest `manifests/date=YYYY-MM-DD/hour=HH.json` listing exactly those files with their row counts, then removes the hour's files the manifest does not list that belong to an earlier export (a lower id, or none) and are at least 10 minutes old. A crash before the manifest leaves the previous manifest and its files intact. An export id never repeats one already present for the hour. Files and their directories are synced before and after the rename.
- The archive directory expects one writer at a time. When two natslens processes export the same hour at once (a rollout overlap), the age rule keeps each one's fresh files until its manifest lists them, so the overlap leaves unused files but never a manifest that names a removed file.
- The export runs on its own goroutine every interval, at most six hours per tick, so catching up never delays an epoch.
- Every export tick writes `state.json` with the highest epoch number, event ID and mute ID; shutdown writes it once more after the last events. A rebuild continues numbering after the higher of those and the loaded rows; only numbers handed out after the last tick before a database was lost are used again.
- `findings` and `mutes` are written whole with every hour; a rebuild keeps each finding's copy with the newest `updated_epoch` and each mute's newest copy (the lifted one once it was lifted, else the one with an acceptance's growth). `archive_hours.mute_changes` records mutes plus lifted mutes plus acceptances with a growth at export; when the current number differs, the newest hour with epochs or events is exported again (provisionally while it is open), so the archive's newest hour always holds the current mutes and older hours are not rewritten. A mute changed while the database has no epoch or event inside the retention window is archived with the next hour that has one. Transitions and check runs are archived and swept with their epoch.
- Archive retention: after a successful export, at most once an hour, every archived hour that ended more than `archive_retention` (default 90d) ago is removed: its data files of every export first, then its manifest, so an interrupted prune leaves a manifest the next one finds again, then the day directories left empty. `0` keeps every hour. The setting must be `0` or at least `retention`, so a rebuild never misses an hour. Apart from that and the superseded files of an hour exported again, the tool never deletes archive files.
- Start warns when an `archive_dir` set in the file is inside the system's data directory, as one lost volume would then lose both. The default, `<data dir>/archive`, is not warned about: leaving `archive_dir` unset is the documented choice of one volume.

### Data history archive status

The archive state comes from the running archiver’s manifest listing and later exports, not `archive_hours`. That table includes exports already pruned and, after rebuild, only hours loaded into the database. The archiver lists at most once an hour after a successful export, also when archive retention keeps every hour. Its status carries listing time, hours and their bounds, newest-hour finality, last export, and the newest failed tick’s error and time; a successful tick clears that error. Before the first listing the hour count is unknown. `GetDataHistory` returns that latest state even for a historical range. These status choices are proposed, not yet confirmed.

### Rebuild

A rebuild runs when the database file is missing or holds no epoch and no event, and the archive has complete hours inside the retention window. It loads only hours with a manifest, exactly the files it lists, and stops when a file's row count differs from the manifest (removing that manifest rebuilds without the hour). It writes `natslens.duckdb.rebuild` and renames it into place only when the load succeeded, so a failed rebuild is tried again on the next start. A table whose rows are updated in place keeps one copy per key: the identity and configuration tables the one with the highest `last_epoch`, findings the newest `updated_epoch`, mutes the lifted copy (else the one with an acceptance's growth), and events the copy received last (a Kubernetes Event moved to a later hour). Rows are matched to columns by name: a column added by a later migration is null in rows loaded from older files, so a migration that adds a NOT NULL column to an archived table must give it a default.

## Checks

### Files and engine

A check is a file `checks/<code>.sql`: a YAML header inside a `/* ... */` comment at the top, so the file stays one runnable query, and one SELECT. Header keys: `code`, `name`, `entity`, `category`, `severity`, `severity_rule` (in words, when a row gets another severity), `kind`, `lookback`, `thresholds` (each with `name`, `default`, `unit`, `description`), `description`, `remediation`, `related_config`, `value_name` and `value_basis` (what the `value` column measures, with its unit, and how; every check that returns a value sets both), and `suppressed_by` (checks of the same entity type whose finding for an entity makes this one's redundant: stream-009 is quiet for a stream while stream-001 fires for it).

The query returns one row per failing entity with `entity_key`, `detail` and optionally `severity` (else the header's), `value`, `cause_event_id`, `related_config` (a JSON object of setting to value), `related_source` and `condition_since` (when the condition began, where the check knows it: `server-004` the process start, `stream-008` and `consumer-009` the newer creation time). A wrong column, key shape, severity or a repeated entity makes the run an error. It reads its inputs with DuckDB's `getvariable()`, set on the connection before it runs: `epoch`, `epoch_time` (the epoch's start), `prev_epoch`, `restart_window`, `archive_since` (when this process began exporting to the archive, from `Engine.ArchiveSince`; NULL in `natslens once` and `natslens checks`, which do not export), and for a check with a lookback `lookback`, `lookback_text`, `window_start` and `window_epoch`, plus its thresholds (a duration threshold is an INTERVAL). Load fails for a variable that is neither reserved nor declared, and for a declared threshold the query never reads. Threshold values are plain finite decimals, except a version threshold (unit `version`, one to three dot-separated numbers such as `1.37.0`), which the query reads as text (`client-008`).

The prelude defines macros on the checks' connection: `ns_text(ns)` writes nanoseconds as `7d`, `30s` or `1.5ms`; `restarting(lo, hi)`, `recovering(lo, hi)`, `planned_down(e)` and `not_ready(e)` describe servers that cannot be taken at their word (see Restarts); `gap_text(names, whys)` names the not-ready servers that may hold a missing asset; `account_lookups(e)` is each account of epoch `e` with its newest `account_details` row at or before `e`, read at most 24 hours before `e` started (the Accounts page's rule, `api.AccountDetailsMaxAge`), and its readable name as `title`; `expiry_text(t, now)` and `span_text(iv)` write an expiry and a span for a detail.

After every stored epoch, outside the epoch's transaction, the engine runs every check on one connection, each within `checks.timeout`, all within a budget of half an interval; a check that would start after the budget is an error run. The order of the checks rotates by one each epoch, so a budget overrun does not leave out the same checks every time. Measured on 7 days of synthetic data (20,000 epochs, 3 servers, 30 streams, 60 consumers, 90 raft groups, 500,000 events) all checks together took about 170 ms.

The engine then writes, in one transaction, a `check_runs` row per check (`ok`, `error` or `disabled`), so the status timeline can tell no data from OK, and the changes to `findings` and `finding_transitions`: a new failing entity starts `firing`, a severity change is `changed`, an entity no longer returned is `resolved`. Transitions carry the epoch's start time, not the wall clock. A finding is flapping when it went through more than three cycles (resolved transitions) in the hour before the epoch; `transitions_last_hour` counts all transitions. Every transition is also written as an event (source `finding`, kind `finding.firing`, `finding.changed` or `finding.resolved`, timed at the epoch's start, with the entity's account, stream, consumer, server or client in its columns and the transition in `raw`), in the same transaction, so that the event list and the timeline show findings with the NATS events.

The writes are one statement per batch of 5000 rows, the batch passed as one JSON parameter; 3000 new findings take about 50 ms. A failed write rolls back whole, so the epoch can be applied again. A value that is not a finite number is stored as NULL and logged. If the store is handed the same entity twice, it keeps the first row.

`system-001 Check failed to run` is built into the engine: one finding for the system while any check failed in the epoch, its detail listing them, critical once the same check has failed ten epochs in a row. A failed check leaves its own findings as they were, since nothing is known. A disabled check does not run, has a `disabled` run, and its findings resolve; so do the findings of a check that no longer exists in the binary.

Thresholds and lookbacks are overridden per check in the configuration file; an unknown code, threshold or value stops the start. Mutes apply when findings are read, not when they are written.

The retention sweep keeps the current episode of every finding it keeps (from its latest firing transition on), so a finding firing since a swept epoch still says when it started; resolved findings are swept once their last change is older than the oldest kept epoch. After a rebuild a finding's episode starts at its oldest loaded transition.

`natslens checks run` opens a database read-only, needs the binary's schema version, and stores nothing; it is for trying a check, not for catching up missed epochs.

### Codes

Codes generally use `<entity>-<NNN>`: `server-`, `account-`, `stream-`, `consumer-`, `client-`, and `system-` for the meta group and the engine. `server-026` reports a system finding because a remote leaf site can move between hubs. There are 89 checks: 86 SQL files and the built-in `system-001`, `server-025` and `server-026`. Account findings are keyed by the account identifier (the public key in operator mode), and their detail starts with the readable name. The inventory checks are `stream-011`, `stream-012`, `consumer-010` and `consumer-011` (a missing KV bucket or object store is its stream, `KV_<bucket>`, `OBJ_<bucket>`). Client findings are keyed by connection name across connections (`(unnamed)` without one), so a mute or a finding survives reconnects; the detail names the server and cid.

The set covers:

- Health: server not reporting, healthz failing, JetStream not ready, meta leader missing or changing often, meta group falling behind (`system-004`), stream or consumer quorum lost, replica offline, replica lagging, raft group catching up for too long, raft write error, a mirror or a sourcing stream lagging, a mirror error (`stream-015` to `stream-017`), a route or gateway missing between servers that answer (`server-017`, `server-019`), bytes queued on a route or gateway (`server-018`), JetStream API errors high (`server-021`), an internal queue backlog (`server-022`), CPU saturated (`server-023`), OCSP peer connection rejected (`server-024`).
- Agreement between servers: the meta group's size differs from the JetStream servers that answer (`system-005`), mixed JetStream API levels (`system-006`), stream or consumer configuration differs, creation time differs, peer set differs, an asset missing on an assigned server (`stream-010`, `consumer-012`).
- Expected inventory: a stream, consumer, KV bucket or object store in the inventory file is missing, or has configuration that differs from it.
- Disappeared assets without an inventory: a stream (`stream-014`) or durable consumer (`consumer-013`) reported within the lookback that no server reports now.
- Consumers: backlog growing, ack pending near max, redeliveries high, max deliveries reached (from events), no delivery while messages wait, push consumer without a subscriber, oldest unread message about to expire (`consumer-014`), pull requests at `max_waiting` (`consumer-015`), a single-replica durable on a replicated stream (`consumer-016`), paused for a long time (`consumer-017`), a work-queue or interest stream without any consumer (`stream-020`).
- Storage: server store above a share of its limit, store full soon, stream near its message or byte limit, stream reaching its byte limit soon, stream without any limit, one replica in a cluster of three or more (`stream-018`), a KV bucket's history without a byte limit (`stream-019`), many interior deletes (`stream-021`).
- Clients: slow consumer disconnects, stalled clients, high pending bytes, high round trip time, connection churn, stale connections, a client reconnecting repeatedly, short-lived connections (`client-005`), repeated authentication errors (`client-006`), unnamed connections (`client-007`), an outdated client library (`client-008`), a server near its `max_connections` (`server-020`).
- Change: server restarted, version differs from the majority, configuration reloaded, stream configuration changed (from events).
- nats-lens itself: a check failed to run (`system-001`), collections often incomplete (`system-007`), archive export behind (`system-008`), event messages dropped (`system-009`), notifications not delivered (`system-010`).
- Accounts and credentials: an account near its JWT's connection or JetStream disk limit, an account JWT or the user JWTs of its connections expiring soon (`account-001` to `account-004`), and a server's listener TLS certificate expiring soon (`server-016`).

What the set merges or measures differently:

- A raft group without a leader is `stream-001` and `consumer-001` (quorum lost covers no leader) and `system-002` for the meta group; a separate raft check would report the same group twice.
- nats-server reports no memory limit, so `server-008` compares a server's memory with the median of the others.
- Slow consumers, stalls, churn and stale connections count a counter's growth over a lookback (15 or 10 minutes) per server process, not since the previous epoch, so one event does not fire and resolve within a minute.
- Replica lag is the leader's raft lag (operations), not a difference in last sequence between replicas, which the servers report at slightly different moments.
- Consumer backlog growth needs the backlog to grow in both halves of the window, so one burst does not fire it; fill rate is the backlog's growth plus deliveries (redeliveries included), drain rate the deliveries.
- Growth forecasts (`server-014`, `stream-006`) take the smaller of the two halves' slopes and need both positive.
- Severity at a stream limit follows retention: work queue and interest streams with discard old lose unprocessed work (warning, critical); limits streams with discard old are ring buffers (info, no forecast).
- Push consumers without a subscriber are checked for durables only: the server removes an ephemeral push consumer (a KV watcher) itself.
- `consumer-003` is critical only when the consumer sat at `max_ack_pending` with messages waiting for `min_epochs` epochs and neither its ack floor nor its delivered sequence moved for `ack_wait`; a pool at the limit that acknowledges is "pool saturated", a warning.
- `consumer-014` dates a consumer's oldest unread message by the stream's history, as nats-lens stores no message times: a message was published no later than the start of the first collection in which the stream leader's last sequence reached it. Without a filter and without deleted sequences in the stream, the message is the one after the ack floor, or after the delivered sequence when nothing is unacknowledged, and the age reads "about"; otherwise, as the next sequence may not match the filter or may have been deleted far earlier, the newest delivered message or the start of the backlog gives a lower bound, which reads "at least". Each stream's history is read back to its own `max_age` plus the lookback only, so one stream with a long `max_age` does not widen the scan of the others, and a backlogged consumer's start is searched among every 64th collection and then the 64 before, after the newest two collections in a row in which no message waited (one alone, as a new leader may report, does not restart the age), so each refinement examines at most 64 collections per point. The refinement also bounds the history scan by the smallest coarse epoch minus 63 and the largest coarse epoch. These bounds let DuckDB prune row groups before joining consumer identities; DuckDB 2.0 otherwise builds a hash table from the full history before applying the block condition. The bounds retain every row admitted by the per-point predicates. This optimization is proposed, not yet confirmed. A message older than that reads younger; an age reads older only when sequences after the consumer's position were deleted, or when messages that waited left the stream while newer ones kept the backlog from emptying. It fires only while the consumer is not catching up (its oldest unread message got younger by less than a tenth of the lookback's span), so a durable replaying a stream quickly does not fire it. Its thresholds (0.8 of `max_age`, critical 0.95, resolve 0.7, lookback 10m), `consumer-015`'s (at `max_waiting` with messages waiting in 2 epochs, resolve 0.9, `max_waiting` of at least 2), `consumer-016`'s info severity (limits streams only, as nats-server runs consumers of work-queue and interest streams at the stream's replica count) and `consumer-017`'s `max_paused` of 2h were chosen by the session that built them: proposed, not yet confirmed. ### Restarts

A rolling restart must raise nothing above info except replicas offline or behind while they are (`TestRollingRestartRaisesNothing`). The prelude separates three states:

- Restarting (`restarting()`): the server's process started within `checks.restart_window` (10m) and replaced an earlier process of the same name. The restart is dated by the process start, not by when natslens first saw the server ID, and needs an earlier process, so a server is not restarting just because natslens or a new cluster started. Only a process restart makes a server restarting.
- Recovering (`recovering()`): HEALTHZ reports a JetStream error, or its raft groups catch up. A server in trouble shows the same, so these never hide its reports; they only add to a restarting server's reasons in the detail text.
- Not ready (`not_ready()`): may hold an asset without reporting it: missing, restarting, JetStream not ready, or answering with JetStream disabled or without JSZ. It is planned when the server is restarting or announced its shutdown, and ready again when the only reason is a restart and it answered JSZ in the epoch. `planned_down()` lists the missing servers that announced lame duck or shutdown within `restart_window`.

The rules built on them:

- Quorum (`stream-001`, `consumer-001`) is judged from the leader most reporters name, and must be lost for `min_epochs` (2) epochs. A restarting server's report is left out only while the healthy servers (neither restarting nor recovering, nor reporting the asset without a leader) can form a majority of the replicas, and never a report that says leaderless or, as leader, fewer than a quorum online. A leader the others name that does not report, with fewer than a quorum of replicas reporting, is a loss. `stream-009` uses the same majority rule and two epochs, and also leaves out a restarting or recovering server's view that is a strict subset of the majority's.
- A server missing after it announced lame duck or shutdown is `server-001` at info for `restart_window`; a crash sends no announcement and is a warning. With half the servers missing `server-001` is critical and its detail counts the streams and consumers left without a quorum; the per-asset findings stay, because `suppressed_by` needs the same entity type and they say when each asset recovers.
- `stream-002` is info while the offline replica's server restarts or announced its shutdown.
- A missing asset (`stream-011`, `consumer-010`) or a disappeared one (`stream-014`, `consumer-013`) is weighed against the servers that held it when last reported (any server when it never was), counting a holder that is ready again as ready: critical with a delete event since its last report (the detail names the client), when no holder is not ready, or when the ready holders that lack it are a quorum of its holders; otherwise info when every not-ready holder is restarting or announced its shutdown, else warning. All four name the last holder and time. For `consumer-013` its stream's delete counts, at warning when the stream was created again; an asset stays a candidate past the lookback while a server that held it has not answered since, and the detail names any collector gap between the last report and now.
- `system-004`, `system-005` and `system-006` fire when their condition held in every epoch from the newest one that started at least `min_duration` before (5m, 10m and 30m) up to the current one, that epoch starting no more than twice `min_duration` before, so a long collection gap is not held; a firing finding resolves only after `min_duration` without it. An epoch with a restarting server, or (`system-004`, `system-005`) one new to nats-lens within `restart_window` of its first epoch, counts as clean, and its own report is left out, so a rolling restart or upgrade fires none of them. An epoch without the meta leader's own row (`system-004`, `system-005`) or without a JetStream server (`system-006`) is unknown: it neither breaks the hold nor counts towards resolving; while it stays unknown, a firing `system-004` or `system-005` stops being reported about twice `min_duration` after its last bad epoch, as no older epoch is read, and `system-002` covers the missing leader. `system-004` reads peers not current from the meta leader's row only, as nats-server leaves a follower's view of the other followers not current, and subtracts the offline peers that `server-001` and `system-002` report; JSZ's meta `pending` counts the JetStream API requests queued on the server, not meta operations behind, and is not read. `system-006` compares levels within a JetStream domain, as `system-005` does. `system-005` compares within a JetStream domain and counts only answering servers, so a peer that stopped answering stays `server-001`'s. `system-007` leaves servers that answered nothing to `server-001`, leaves out a server restarting or announced within `restart_window`, and does not count the store's notes (`note: `) in `epochs.errors`. `system-009` leaves out slow consumer reports of the collector's own connection, which carries monitoring replies. `system-008` counts the wait from the end of the hour or from `archive_since`, whichever is later, so the catch-up after a restart does not fire. The thresholds and severities of `system-004` to `system-009` are proposed, not yet confirmed.
- Proposed, not yet confirmed: `system-002` and `system-003` retain the system entity and its empty key, preserving finding IDs, mutes, acknowledgements, notifications, and API shapes. Their evidence is computed per physical group when stored RAFT peer names resolve uniquely to observed processes and prove that scope. Unobserved name-derived peer hashes provide no physical identity: shared hashes across otherwise separate membership components leave every affected component unscoped, including transitive bridges. A shared down peer within one already connected component does not remove its scope. Domain labels, server cluster names, JSZ's leader-cluster name, and the reused `_meta_` group ID are not group identities. A JSZ-only reporter attaches only to an unambiguous leader in a proven group. `system-002` reads the current collection; `system-003` reads its bounded lookback, with no future membership or process replacement. Each check returns one system finding listing affected groups; the flapping value is the maximum group count. With proven groups, unresolved advisories and unscoped snapshot changes are excluded from group thresholds; uncertain components can therefore have undetected flapping. When no groups can be identified, the legacy aggregate flapping detector remains explicitly unscoped and cannot certify changes within one physical group or independent groups. With observed but unresolved membership, explicit empty-leader replies fire independently of healthy or missing replies, with the detail naming only those empty-leader reporters. With no membership evidence, `system-002` retains the legacy aggregate so a rolling restart with mixed replies does not certify a leaderless group; that fallback can hide independent leaderless groups. The internal mapping carries whether membership was observed to distinguish these cases. Missing leader and peer counts do not become healthy zeroes; absent evidence can still resolve a finding because the finding model has no per-group unknown state. The Overview leader and time series retain their separate system-wide majority semantics.
- `system-003` allows 4 meta leader changes in 15m and does not count the first change away from a server within two collect intervals (the median gap between epochs) after its announcement or after its replaced process last answered; a later hand-over, as with a lame duck period longer than about a minute at a 30-second interval, is counted.
- Tooling connections are left out of the client checks (`client-001` to `client-008`) and of `server-011`'s client list unless `checks.include_tooling` is set: nats-lens's own connections (`nats.name`, `<name>-events`, `<name>-<account>`) and clients connected from 127.0.0.1 or ::1, which is how a port-forwarded CLI appears. The loopback rule is `checks.loopback_is_tooling` (on by default) with a guard, as a sidecar can make every inbound connection look local: the share of loopback clients among the connections that are not nats-lens's own is taken over the last 10 epochs, the rule stops when it goes above 60% and returns only when it falls below 40%, and an epoch with fewer than 3 such connections keeps the previous decision, so a lone CLI stays tooling unless the guard is already off and a thin epoch does not reset the guard. After each epoch's checks the engine stores the decision in `epochs.loopback_tooling`, made from the latest decision stored in the trailing window (an epoch whose checks failed has none and does not reset the guard) and the trailing share, so an epoch is judged the same whenever it is read; an epoch without one (older data) counts as on, and the column is archived with the epoch. Each epoch's rows are judged by that epoch's decision; natslens logs it once when the guard drops the rule. The prelude macros `tooling_at(name, ip, epoch)` and `tooling(name, ip)` (the epoch checked, for events) decide, from the reserved variables `exclude_tooling`, `tooling_names`, `loopback_setting` and `loopback_now` (the decision being made) and the stored decisions. The API's pages share one copy of the rule outside the checks (`storeprov/tooling.go`): `toolingRule` for a connection of an epoch, in Go and as an SQL condition, and `eventToolingSQL` for an event, judged by its epoch's decision; the Connections page, the Overview's clients tile, Replay's reconnects and the routine events use it. `ListConnections` leaves tooling connections out unless `include_tooling` is set and counts them in `tooling_hidden`. `server-011`'s count comes from the servers' connection counters, so it still includes them. The API marks such connections `tooling`.
- `client-004` counts reconnects, not connects: the smaller of the `client.disconnect` events whose reason is neither "Client Closed" nor "Server Shutdown" and the `client.connect` events of the same name in the window, paired in either order and from any host, so instances sharing a name are merged. A service scaling out (one name, many hosts, no disconnects) does not fire it.

Checks do not read Kubernetes events yet; the restart rules rely on process start times and lame duck and shutdown announcements.

### Inventory and mutes

The inventory file lists per account the streams (with their durable consumers), KV buckets and object stores that must exist, and the settings that must have a given value; a setting left out is not compared. Byte sizes take binary suffixes only (KiB to TiB), because NATS tools read `GB` differently. It is loaded into `inventory` on every start.

An operator can mute a check, or a check on one entity, with a reason and an expiry. Muted findings still record but are shown apart and do not alert. A mute without an expiry is not allowed. An operator can also accept one entity's finding as by design, with a reason and a review date; an acceptance is a kind of mute (see "Accepted findings" under the API).

### Notifications

Notification design choices in this section are proposed, not yet confirmed. The implemented behavior is documented in [Notifications](features/notifications.md); the [README](../README.md#notifications) holds configuration and the versioned webhook contract.

Only `natslens run` reconciles and delivers findings. After a check run, the reconciler compares each channel's selected, unmuted firing findings with its `notify_state`. The comparison queues messages and advances state in one transaction. This state describes the channel's queued view; it does not wait for HTTP success. A `kinds` filter drops messages without withholding state changes. `once` and `checks run` do not queue notifications; a later `run` compares the resulting view instead of replaying every stored transition. Notification delivery starts before NATS connection setup, so pending messages can retry while NATS is unavailable.

Each channel's first reconciliation establishes a baseline: the selected firing findings become known, and one summary carries their count. No individual opening messages are queued. Removing a channel removes its state and queue during a sweep; adding it again establishes a baseline. Notification state, outbox rows, rate watermarks and database identity are local delivery state, excluded from Parquet. Reopening a database preserves them. A rebuild creates a fresh baseline and does not recover pending deliveries. This avoids replaying old incidents to a receiver after a rebuild.

Each system has independent delivery workers per channel. The worker pins the oldest batch of at most 100 rows, its boundaries and timestamp before HTTP. A pending head prevents later messages overtaking it; another channel keeps delivering. A successful batch requires another stored collection before the next batch. After a terminal outcome, the channel also waits one collection interval. Durable watermarks preserve these limits across restarts and retention sweeps.

Delivery is at least once. A crash after a receiver's 2xx but before the outcome write can repeat the request. The webhook `Idempotency-Key` contains a random database incarnation, system, channel and first and last outbox IDs. Reopening preserves the incarnation; rebuilding creates a different one so reused row IDs cannot collide with old batches. Message deduplication keys name the system, finding episode, kind and reconciliation epoch; acknowledgement replacements also carry their acknowledgement ID. Receivers should scope message keys to the channel and batch incarnation when deduplicating across rebuilds. Slack-compatible requests have no idempotency header.

A 2xx succeeds. Network failures, timeouts, 5xx, 408 and 429 retry with exponential waits from 10 seconds to 10 minutes. A `Retry-After` on 429 or 503 can extend that wait up to 10 minutes. Other responses, including redirects, are terminal refusals. A still-failing batch becomes failed after `give_up_after`, measured from its oldest queued row. Pending rows survive restart. Terminal rows expire after the shorter of seven days and system retention, with at least one hour after the outcome for reporting. The four notification gauges count messages, and last-hour outcomes use completion time. `system-010` warns about messages pending longer than `pending_for` (10 minutes) and becomes critical for a refusal or give-up in the last hour. Another channel or external metrics must report a failed receiver.

Mutes and acceptances close a channel's known view with `muted`. An eligible finding re-enters when coverage ends. Flapping sends one notice and holds ordinary transitions until flapping ends. Acknowledgements send the actor, note and quiet time only while the finding is in that channel's view. Quiet suppresses reminders and severity decreases, including a fall below the channel threshold; rises and actual resolves still send. A channel remembers that its known episode was acknowledged, so a flapping resolve still sends after release, expiry or restart. That memory does not transfer to a later episode or another channel. Upgrades restore it only from provable channel-local history; ambiguous historical episodes keep the ordinary flapping hold. Quiet ending sends one reminder for a known still-firing episode even when regular reminders are disabled. A simultaneous rise also sends `changed`; a fall below the threshold closes with `resolved` after the reminder. Replacing an acknowledgement sends the replacement note; extending quiet does not end it. Gaps reconcile the current view and notes since the channel's previous reconciliation, rather than every past firing and resolve.

Destinations are configured only. HTTPS uses the system trust roots; loopback HTTP is allowed for local tests. Redirects are refused. A channel's URL and bearer token can come from a file or environment variable, read at each attempt. A file rotation takes effect without restart. Unreadable secrets warn at startup and retry during delivery. Logs identify the channel and destination host, never its secret URL path, query or token. The database stores messages, outcome codes and generic failure information, not receiver credentials or response bodies. No store lock spans the HTTP request. NetworkPolicy egress must allow DNS and the configured receivers. The notifier never connects to NATS.

## API

Connect service `natslens.v1.LensService`, protobuf in `proto/natslens/v1/`, served under `/api/` by `natslens run`. Connect handlers also speak gRPC and gRPC-Web; the server enables HTTP/2 without TLS. TypeScript is generated with `protoc-gen-es` v2 only: connect-es v2 reads the service from those files and needs no plugin of its own.

### RPCs

- `GetLensInfo`: the identity mode (verified IAP user, or a name in the request), version, cluster, collect interval, retention, and whether the data is live or the demo, and the provider's now (`now`), where a range without an end ends. The UI reads the identity mode to decide whether the mute dialog asks for a name. It is its own RPC because it does not depend on a range.
- `GetDataHistory`: a system and range return history start, newest collection and oldest event, retention and collect interval, coverage, gaps and totals, archive state, history requirements, and firing findings already true at history start. The handler applies the common range validation and query timeout; the provider reads facts and `FinishDataHistory` applies shared rules for the store and demo. These RPC choices are proposed, not yet confirmed.
- `GetOverview`: cluster name, freshness (with `collecting`, false while the collector's connection is not connected or closed, and `not_collecting_since`: from the runtime's collection status, else from the collector's stored connection events), servers, the finding tally (critical, warning, info, muted, flapping, resolved in 24 hours), the worst unmuted finding, number tiles with their series and descriptions, and time windows to shade.
- `GetShellStatus`: what the web UI's shell reads on every page, in one call per system. The system's freshness, servers and finding tally over the range, read as `GetOverview` reads them but without its tiles, windows and the check runs the tiles need; an unset range is the last two collect intervals of the system's provider. That part has 10 seconds (`ShellTimeout`); a failure or timeout of it is reported in `error_code` (the Connect code) and `error` (the text a failed call would carry) with everything else still served, so the shell keeps its system list, badges and landing when one system's store is broken or slow, and the header shows the error as it shows a failed call; a caller that goes away still ends the call. Every system's badge state, in configuration order: status, collection state, whether it collects (false while the collector's connection is not connected or closed, has an error, or the freshness says it does not collect, the rule the Fleet page applies to a summary), the summary's error, and `pending`. A badge comes from the system's summary over the last 24 hours with one strip bucket, through the same shared runs and 5-second limit as `ListSystems`; a summary read without an error is kept for its freshness's collect interval (30 seconds when it names none), then served once more while one read in the background, never bound to a caller, replaces it. - `GetReplay`: the story of what changed between two moments A and B of one system, for the Replay page. A and B are required, A before B, at most 24 hours apart once a B after now is read as now; anything else is invalid_argument before the provider is asked. The provider refuses an A older than the retention as invalid_argument ("A is older than retention (14d); Replay reads the database only"), as Replay reads the database, not the archive. The call has the usual 30 seconds. The provider reads the facts (`api.ReplayFacts`) and the handler words them with `api.FinishReplay`, which the store and the demo share, as `GetPlacement` shares `FinishPlacement`. The collections at A and B are the newest that started at or before each, within three collect intervals. The steps: Kubernetes node drains and upgrades and NATS pod failures; restarts (a process that replaced an earlier one of the same name, started after A and was first collected by B, as `server-004` pairs them; one first collected after B makes its server a stop that answered again after B), a span from the old process's last answer to the new one's first, with the lame duck or shutdown announcement of the restart window before it (each announcement goes into one step only), the NATS pod events, the streams and consumers it led elected elsewhere, and what it held before and after, from JSZ; servers that answered in the collection at A or later and not in the one at B, with when they answered again after B and the streams and consumers they led elected elsewhere; meta leader changes (an election that keeps the leader makes no step) and the other leader elections, folded by the new leader; quorum losses of `stream-001`, `consumer-001` and `system-002` as spans, from the firing that started them (before A for a loss already open at A) to their resolve, with the quorum advisories; gone assets (below); other warning and critical firings and changes, folded by check; resolves; and gaps: no collection for more than three intervals (leading and trailing ones included), `collector.gap` and `collector.k8s_gap`, each gap step with its `gap_kind` (collections, collector, Kubernetes) so that the page can say which counts it left unset without reading the title. Steps of one fold key within the longer of 2 minutes and 2 intervals fold into one, with a count. Info findings are only evidence. Every step names its evidence (an event, a finding or a collection; an election's evidence names the server it elected in `elected`, and a restart, stop or leaders step counts all its elections by new leader in `leaders_taken`, as the evidence is capped; a capped step keeps its own evidence first and fills the rest with elections); no step is written without one, except a gap, and no step claims a cause. Steps are in time order, then by kind (Kubernetes, restart, leaders, quorum, gone, finding, resolved, gap), then ID; at most 200 between A and B, keeping critical, warning, restart, gone and gap steps first, and at most 10 evidence and 50 entities each. After B, up to the earlier of now and B plus 6 hours, the first resolve of each warning or critical finding with a step and a stopped server answering again are at most 10 steps marked outside the range. A gone asset is a stream, or a durable consumer by the rule of `consumer-013` whose stream is not gone, that a server reported at A's collection and none at B's, with its holders at A, those of them without a JSZ reply at B, its last report, its delete event as `consumer-013` matches it up to B, a gone stream's durables, and its findings of `consumer-013`, `stream-014`, `consumer-010` and `stream-011`, a gone stream's also those of the durables that went with it; at most 200. The counts are unset when not observed: restarts and findings raised need a collection between A and B, stops also the collection at B, the gone counts both collections and a provider that read the gone assets, the leader, quorum report and reconnect counts a stored event up to B and every connection that captures events connected over A to B (a `collector.disconnected`, `collector.not_connected` or `collector.connection_closed` of a connection other than the collector's, until its next `collector.reconnected` or the next `collector.started`, is a gap step of kind events, unless it reconnected within 10 seconds (a failover: advisories of those seconds may be missing, but nothing is unset); a start ends every open loss, and an events connection that does not connect after a start is a loss only from its `collector.not_connected`, 30 seconds later, so those seconds count as captured (a known limit, kept for simplicity); a redialled events connection records `collector.reconnected`; any one lost connection unsets every event count, though each carries only some of the events; collections do not tell, as events come on connections of their own), and the node counts `kubernetes.enabled` (`storeprov.Provider.Kubernetes`), the pool count also a node pool label. A time nats-lens was not running (`collector.gap`) that overlaps A to B (a gap starting at B included) unsets the event and node counts, and a Kubernetes watch gap (`collector.k8s_gap`) the node counts; a node event that names no node unsets the node counts too (a node's own Event names it as the Event's object, and the watcher also writes `node`, `pool` and `kubelet_version` on it). Each unset count has one entry in `unobserved`: the count's name, the first cause that applies in `FinishReplay`'s order, and the span behind it (of a gap the earliest that overlaps A to B, to unset while it had not ended; of the read limit where the read ended). The causes, in that order: for restarts, stops and findings raised, no collection between A and B, then (stops) none at B, then (findings) the read limit before B; for the gone counts, no collection at A, at B, gone assets not read; for the event counts, no event stored up to B, nats-lens not running, a connection that captures events without a server or closed, then (all but reconnects) the read limit before B; for the node counts, Kubernetes not watched, nats-lens not running, a Kubernetes watch gap, a node event without a node, then (pools) an upgraded node without a pool label. The proto comment on `ReplayUnobserved.reason` lists the same order. A set count has no entry, so the page reads the reasons instead of deriving them. A step says no lame duck or shutdown announcement was captured only when events were captured and read over its whole announcement window, which may start before A: both providers read events and collector gaps from the restart window before the earlier of A and the collection at A, and a window that starts before that read never claims an absence. Client reconnects pair disconnects and connects per name as `client-004` does, with disconnects of a server stopping counted and tooling clients left out by the rule of the routine events. The store reads at most 20,000 events and 20,000 transitions, the earliest; when the limit cuts them the response says the steps are truncated, gives in `complete_until` the time before which both were read in full (also when the read reached past B, as steps after B beyond the cut may be missing; the counts then stay set), leaves the counts taken from the cut rows unset unless the read reached past B (then every row of A to B was read), and does not call a quorum loss open at B when its resolve may be in the cut transitions. The demo builds its facts from its scenario (see Demo). The page reads the strip from `GetStatusTimeline` (`include_ok`), so the RPC has none.
- `GetTopology`: how the servers of a system connect, for the Topology page. It reads the range's newest epoch, as `GetPlacement` does (none in the range: the empty response with `epoch` 0), from the tables the collector already writes (`routes`, `gateways`, `leafnodes`, `epoch_endpoints`, `servers`, `server_stats`), with the usual 30 seconds. The provider reads the epoch's rows, the routes of the collection before it for the slow rule, and the drops of the window before it (`api.TopologyFacts`), and the handler applies the rules with `api.FinishTopology`, which the store and the demo share. Clusters: the servers the epoch expected, answered or missed, by cluster, each with its process of the epoch's cluster and tags; a server without a cluster (no stored identity) is placed in the cluster of a server whose route names it, else in the cluster with an empty name, which the page labels as not known, and its routes, gateways, sites and drops count in the cluster it is placed in; a cluster's place is the value of a `region:` tag every server of it carries; the meta leader is the majority's (`metaLeaderAt`), streams led the sum of `js_streams_leader`. Gateways: every two clusters with a gateway row in the epoch or an outbound gateway row in the 24 hours before, so a pair down in the epoch is listed with 0 connections and sorts first (a cluster that was removed shows so too, until its last outbound row leaves the 24 hours), then by drops in the last hour, connections missing and round trip; connections and round trips (highest and median) from the outbound rows with a connection ID, as every gateway connection is one server's outbound and another's inbound; expected is one outbound from each server of either cluster that answered GATEWAYZ; pending bytes summed over both directions. Routes: one pair per two servers; the highest round trip of either end's routes, pending summed, the pool the larger count of routes without an account that either end reports, pinned accounts the rest; one-sided when the other end answered ROUTEZ and lists none. The slow rule, per cluster over the pairs that report a round trip (`topology_slow.go`): two servers are near when their round trip is under the larger of 2 ms and 3 times the median, over the measured servers (those with at least one reported pair), of each server's fastest round trip; servers joined by near pairs, directly or through others, form groups. The cluster is judged only when the largest group holds more than half of the measured servers; otherwise it is split into groups of similar size, none of them the normal one, and nothing in it is slow. A server outside that group with a reported pair to it is slow, with all its routes that report a round trip (one with pairs only to other outside servers is not judged); a pair inside the group is a slow link at 2 ms or more and 3 times the median of at least 2 of the group's pairs that touch neither of its servers. No step depends on which pair is the fastest, so jitter that keeps every round trip on its side of a threshold that itself follows the median gives the same result on every refresh. Pairs left unreported cannot make one half of an even split the reference, but a server that reports no round trip at all leaves the measured servers: in an evenly split cluster, a collection in which one server reports none (during its restart, or when its ROUTEZ failed) is judged, and the other group is slow for that collection. Kept so: counting every expected server instead would stop judging a cluster of 4 with one server down and one slow. Results: one slow server stands out in a cluster of 3 or more, two in a cluster of 5 or more (two of 4 raise the typical nearest round trip to theirs, and nothing is slow); a group of fewer than half far from the rest is slow (2 servers 10 ms from the other 3); one server of 3 far from a co-located pair is slow, as one slow server of 3 is; a slow link stands out in a cluster of 5 or more; even splits (2+2, 3+3, 2+2+2, 3+2+2), zones under 2 ms apart, jitter, two servers alone and pairs all alike are never slow; a server measured only against a far server, when half the servers' nearest pair is far, leaves nothing to tell and nothing is slow. A route is slow only when the epoch and the collection before it both find it slow by these steps (`markSlowTwice`), so one spike in one collection marks nothing: the collection before is the newest earlier epoch with route rows that started at most 3 collect intervals before the epoch, the bound of drop counting, even when it lies before the page's range (proposed, not yet confirmed); without one (the first collection, a gap in collecting, epochs without routes) nothing is slow, and a pair that collection did not report, or reported without a round trip, is not slow (proposed, not yet confirmed); with the collect interval not known no collection counts as the one before and nothing is slow (proposed, not yet confirmed). Each collection is judged by the full rule on its own rows, so an earlier collection with only some servers' routes is judged on those. The store reads that epoch's routes in `topologyEarlier`, comparing `started_at` with the bound directly; the demo builds the same from its scenario, and `FinishTopology` ignores a collection outside the bound. A round trip near a threshold can still change sides between refreshes, but a route is marked only after two collections on the slow side. Tests run these cases over 200 seeds of jitter (`topology_slow_internal_test.go`), and a cluster of 30 servers takes well under a millisecond. The rule replaced, in the review rounds, a comparison with the cluster's median (one slow server set it in a cluster of 3 or 4), a comparison with the pairs not touching a route (it flagged zone layouts) and a core grown from the fastest pair (the result followed whichever group held that pair). The owner chose the two collections on 2026-10-26 (see "Owner review of proposed decisions, 2026-10-26").
 A round trip of 0, which a server reports before its first ping, counts as not reported everywhere. Leaf node sites: the epoch's LEAFZ rows keyed by remote name (the IP without one) and account, one row with every hub the site is on (`hub_servers`), leaving out rows in which the reporting server is the spoke (`is_spoke` true: its own uplink to a hub, which migration 0026 now says in the column's comment); a site seen in the 24 hours and not in the epoch is listed as not connected with its last hub and time, and marked `connection_unknown` when a server of the cluster it was last seen on failed LEAFZ in the epoch, as it may be connected there (a failure in another cluster leaves a known disconnect known, and a server that answered nothing is drawn missing and does not make sites unknown); clusters count sites by name, those of unknown state not among the not connected; at most 500 sites, not connected first, then unknown, then drops, round trip and name, with `leafnodes_total`. Drops: NATS sends no event when a route, gateway or leaf node disconnects, so drops are counted from the collections of the 24 hours before the epoch (`drops_window_start`, later when the history is shorter): between two consecutive collections, at most 3 collect intervals apart, a gateway drop is an outbound connection whose connection ID changed or that went away while its server answered GATEWAYZ both times under the same server ID, and a leaf drop a site's connection (hub server ID and connection ID) that went away, the site gone or on another connection or hub, while that hub answered LEAFZ both times. A collection gap, a failed endpoint and a restart (a new server ID) count no drop; a disconnect and reconnect within one interval shows only as a new connection ID, and one that changes nothing is not seen. A count is unset when no two consecutive collections in its window were answered by a server of the pair, or, for a site, by its hub while it was connected. Route drops are not counted. The store counts the drops in SQL (`storeprov/topology_drops.go`), so only the counts per server and remote cluster, per site, and each site's newest row before the epoch leave the database: a leaf connection stored once in each collection from its first to its last can only have dropped after its last, which an aggregate finds, the rare others are read row by row with a window over the next epoch, and each site's newest collection is an aggregate, so no query sorts the window's rows; gaps are compared in microseconds. The demo counts its history with `api.CountTopologyDrops`, the same rule in Go; a randomized test with fixed seeds (`topology_drops_random_test.go`) compares the two over restarts, failed replies, gaps of every length, moves, sites on two hubs, sites keyed by IP and spoke rows. `unobserved` names, per endpoint, the servers whose ROUTEZ, GATEWAYZ or LEAFZ was missing or in error; a server that answered nothing is drawn missing instead. Measured on a synthetic system of 24 servers, 48 gateway rows and 1,000 leaf node sites per collection at 30 seconds: on a file store of 14 days with DuckDB limited to 60% of 256 MiB and 2 threads, a read and finish takes 0.3 seconds and DuckDB's sampled memory reaches its limit; the process's peak RSS varies between runs, measured from 174 to 365 MB on the clean store and 343 and 427 MB when each server's LEAFZ failed once in the day (failed answers send connections to the row-by-row count), so up to about 450 MB at 1,000 sites (641 MB and 1.25 s with the first SQL version); in memory (`TestTopologyLargeDay`) the Go side allocates 2 MB (2.4 GB when every row was read into Go). The peak RSS above 256 MiB meant the earlier base of 256 MiB fitted small systems only; the owner raised the base deployment to 512 MiB on 2026-10-26 (see "Owner review of proposed decisions, 2026-10-26"). That still does not fit 1,000 sites with room to spare: the peak was measured with DuckDB at about 154 MiB, and at 60% of 512 MiB DuckDB may take about 307 MiB. The README's "Memory size" table proposes 1 GiB for hundreds of leaf node sites and 2 GiB, the `gke-iap` example's, for 1,000 (proposed, not yet confirmed).

A client subscription on the deliver subject of a push consumer of the page's epoch names its connection on the stream row and is no row of its own; the others make one row per (account, subject), every `_INBOX.` subject folded into one `_INBOX.>` row per account; a row counts distinct connections (server and client ID), names the distinct connection names in order, at most 3 with the count of the rest, and has a queue only when every subscription shares it. A row per account with JetStream use (a stream, or API requests in the epoch) is `$JS.API.>`, with the requests per second and the share that failed from `account_stats.js_api_total` and `js_api_errors`. Every server reports the account's counters for the whole cluster once the account stores data on any server of the cluster: the servers holding data send their usage, with the API counters, every 1.5 seconds; a server that receives one creates its own usage entry and sends updates too, with its own API counts and no stored data (`TestJetStreamAPITotalIsClusterWide`). Until then each server reports only the requests it answered, mostly the meta leader, and the highest is a lower bound. So the servers are not summed: per server the increase between the first and last report of its newest run in the 15 minutes before the range's end, a run ending where the counter fell (another server's restart takes its share away). A report that may still hold a server's own count before the others' totals arrive is left out: the first report of a server ID and account that has no report in the hour before the window (a new process reports 0 until the updates bring in the running total, which a 5-minute step would read as thousands of requests; a series that returns after a longer gap loses one report), and a report within 60 seconds of the process start (`server_stats.start_time`, else `servers.start_time`). Per account the server with the highest rate wins, the first by server ID on a tie, with its error share. A median of the servers would read 0 in the state before the counters are shared ([0 50 0]); the highest is the better bound. The epochs of the window and the hour before are read first, so both scans of `account_stats` are bounded by epoch: over 115 million reports (4 days of 30-second epochs, 50 servers, 200 accounts; `TestSubjectsAPIRateScale` with `SUBJECTS_SCALE_DAYS=4 SUBJECTS_SCALE_SERVERS=50 SUBJECTS_SCALE_ACCOUNTS=200`) a page took 150 to 220 ms on a laptop, where looking up each series' first report in the whole history took 630 to 940 ms. Known limits: when an account first stores data, every server takes in the others' totals at once, so the rate reads high for up to 15 minutes after the account's first stored message; a server whose routes stay down across several collections reports its own count until they come up, and its jump then reads high; a server clock skewed so that a report still holding its own count passes the 60-second rule after its first report can let a jump through. Mirrors and sources link streams of one account by name: `stream_config.sources` keeps a source's name without its account or filter, so a source from another account links to a stream of the same name in the stream's own account, and a source's filter is not applied. Overlap is `server.SubjectsCollide` between two streams' subjects in one account, found without comparing every pair: `overlapsOf` splits an account's subjects by their first token, compares those with a wildcard there (or no token left) with all others, and splits each literal group again by the next token, as two subjects overlap only when each token is equal or a wildcard on one side; 10,000 streams with literal first tokens take about 10 ms where every pair took 11 seconds, but subjects that start with a wildcard are still compared pair by pair, so 10,000 streams on `*.events.<n>` take about 2.5 seconds; a test holds it to the pairwise rule; a stream (not a KV bucket, object store or mirror) has no consumer when none is listed and no other stream mirrors or sources it; a subscription row is wide when its subject ends in `>`. Order: overlap or no consumer first; then by account with the system account (`accounts.is_system`) last; streams, buckets and object stores before the other rows; those by stored rate (unset last), the others by connections, most first; then by pattern. The request's `filter` selects rows before the cut of 1,000 and `rows_total` counts them; the five counts are over the scope, whatever the filter, and the account scope applies to every count. `subsz_servers` are the servers with a SUBSZ outcome in the collection and those the epoch missed; answered with `total` (SUBSZ's count of local subscriptions before the limit) and `listed` when `subscription_lists` has a row. `MatchSubject` takes a literal subject (no `*` or `>` token, no empty token, no white space or other control character, at most 255 bytes; else `invalid_argument` before any provider call). A message reaches only the account it is published in (imports and exports are not followed): with an account the answer is that account's alone, also when nothing matches; without one it is one group per account where something matches, as if published there, by account with the system account last, and the system account only for a subject that starts with `$SYS.`. Per account: each stream whose subject matches (`server.SubjectMatchesFilter`) with the first subject that did, its durable consumers whose filter matches (none matches all) and a count of the ephemeral ones, and the streams that mirror or source it; the client subscriptions on a matching subject by subject and queue, unfolded, the servers' own and unlisted ones left out; and `jetstream_api` when the subject starts with `$JS.API.` and the account uses JetStream, as the servers answer it. The store prefilters those in SQL (the subject itself, or a subject with a wildcard whose first token is a wildcard or the literal's) and `FinishMatch` decides. ### Ranges and identities

Reads over time take a `TimeRange`, never an epoch. An unset end means now (live mode), the provider's `Now()`, which `GetLensInfo` reports as `now`; an unset start means 24 hours before the end; a range spans at most 400 days. Lists of entities and the freshness describe the newest epoch inside the range; growth and series cover the whole range.

Every ID is a string: event IDs, mute IDs, finding IDs (`<check code>:<entity key>`), timeline row keys (the check code, plus `:<entity key>` for a row of one entity), lane item IDs (the event ID, or one derived from source, kind and time for a Kubernetes item that is not stored), and connection keys (`server/cid`). Database IDs given as strings must be positive decimal numbers in canonical form.

Entity keys: server name, account, `account/stream`, `account/stream/consumer`, `server/cid`, client connection name; the system entity has none. The account is the one the servers report (the account ID in operator mode); every message of a response that holds an account (entity references, events, connections) also carries its readable `account_name` when known, filled by the handler from the `accounts` table, and the UI shows the name with the ID as its tooltip; event filters by stream or consumer also match the readable account name, because events can carry the configured name. A filter with an unknown entity type or a key of the wrong shape is invalid_argument, never ignored. A connection filter on events matches `client.id` in the payload.

### Data history gaps and requirements

These rules and the use of shared gap helpers by Data history and Replay are proposed, not yet confirmed. `CollectionGaps` finds collection losses longer than three collect intervals, including leading and trailing gaps. Recorded downtime and Kubernetes-watch spans come from collector events; event-connection losses shorter than 10 seconds count as failover, not a capture gap. The store also reads older losses still open before its event window.

Data history classifies not running, not connected, no collections, events not captured, Kubernetes not watched, and before history. It merges overlapping collection losses, with label precedence not running, not connected, then no collections. Event and watch gaps stay separate, even during collection loss. Before-history is added separately and excluded from coverage: the covered span starts at the later of range start and history start. Coverage uses the full merged gap set before truncation. Without history, or when the range ends before history starts, the UI replaces the coverage boxes with its no-collection explanation.

Each response keeps the newest 200 collection/before-history gaps and the newest 200 event/watch gaps independently, with totals for both. A gap retains its true start; its end is unset when open at the range end. Replay uses the shared collection and capture rules for its story; its steps and observation reasons are not the Data history page’s merged display list. These classification and limit choices are proposed, not yet confirmed.

History requirements use configured check lookbacks, six hours for growth over the selected range, 8 days and 1 hour for acceptance growth review, and 24 hours for daily pages and Replay. System-history rows use history through now and flag retention shorter than the requirement; growth has an availability time only when the range follows now and spans at least six hours. These readiness rules are proposed, not yet confirmed; forecast confidence margins remain deferred.

### Remediation playbooks

The remediation-file extension is proposed, not yet confirmed. A check entry accepts plain text or `{text, playbook}` with non-empty text and an optional HTTPS URL. ### Acknowledgements

The acknowledgement model is proposed, not yet confirmed. An acknowledgement is a record apart from `mutes`: it records who investigates a finding without hiding its severity, tally, or badge. It matches the finding and its firing episode (`since_epoch`). Resolve or a later episode stops it applying without writing an end. A replacement ends the prior record as `replaced`; a hand-back ends it as `released`. Quiet expiry leaves the acknowledgement in force, with alerts eligible again. The verified IAP identity or request name follows the mute rule.

An optional note has at most 500 characters. The API accepts quiet from 30 minutes through 24 hours, or until resolved. Saves write `finding.acknowledged` in the same transaction; Events and the finding lane read that non-routine event. There is no acknowledgement-history list RPC. The finding page reads the current acknowledgement and keeps release or replacement receipts only during the visit to that system, finding, and episode. Resolve or a change of system, finding, or episode clears those receipts.

The archive exports whole acknowledgement records every hour, as it does mutes, and rebuild keeps each record's newest copy. `archive_hours.ack_changes` fingerprints IDs and end times so changes or retention sweeps trigger re-export of the newest hour. Older archives have no acknowledgement files or maximum acknowledgement ID and rebuild with none; the sequence continues after the maximum loaded or recorded ID. Retention removes ended records and records of old episodes outside retained history. These archive choices are proposed, not yet confirmed.

While quiet holds, `nats_lens_finding_acknowledged` is 1 with the finding's identity labels, for the entity set selected by the finding-series cap; otherwise it is absent. `nats_lens_findings_acknowledged` counts every firing finding whose quiet holds, muted or not. The UI acknowledgement tally instead includes acknowledgements whose quiet expired. The README's per-finding Prometheus and Cloud Monitoring rules exclude quiet acknowledgements through `unless on(system, code, entity_type, entity_key)`. Notification channels apply their own quiet rules. These metric choices are proposed, not yet confirmed.

### Status and findings

Status values combine severity with muted and no data in one enum (`Status`). Nothing defaults to OK. A server's, stream's, consumer's or tile's status is the worst firing finding on it (a stream's includes its consumers', muted when all are muted); OK when none fires and every check of its entity type ran ok (or was disabled) in the range's newest epoch; no data otherwise: when such a check failed or did not run, for a server that did not answer, for an expected consumer without a finding, and for a tile without a value. Tiles map to checks (`api.TileRules`, which the demo uses too): servers to `server-001` to `server-006` and `system-001` to `system-006` (`system-007` to `system-009` judge nats-lens itself and colour no tile; proposed, not yet confirmed), meta leader to `system-002` and `system-003`, streams, KV stores and object stores each to the stream checks of their own kind of stream (`KV_`, `OBJ_`, the rest), consumers to every consumer check, clients to the client checks, connection churn and staleness and `server-009` and `server-010` (the former connections and slow consumers tiles), storage to `server-007`, `server-014`, `stream-004` and `stream-006`. Accounts has no check, so its status is no data.

A number that was not observed is unset, never zero: tile values, the counts of servers, connections, streams and consumers and of their per-server views, and a consumer's `num_pending` and `num_waiting` without a leader row. A replica's `lag` is unset for the leader, which does not list itself. `consumers_expected` counts the inventory's consumers of a stream the inventory names, and a consumer the inventory expects that no server reports is listed with `present` false and no numbers.

A stream's `bytes_per_day` is the Theil-Sen slope (the median of the slopes between every pair of points) of the leader's bytes over the range, reduced to at most 200 bucket medians, and is unset when the observations span less than 6 hours, so one write is never extrapolated to a day. It may be negative: a KV bucket whose entries expire by TTL faster than they are written shrinks for real, and a slope over 6 hours that one purge cannot move is real. The growth forecasts of the checks (`server-014`, `stream-006`) keep their own rule.

The Findings list, the findings of a server, stream or consumer page, the systems list's worst finding (`ListSystems`, which the shell's badges read) and the Overview's worst finding rank findings worst first by one rule, `api.CompareWorst`, which the store and the demo share: firing before resolved, unmuted before muted, by severity, then among warnings a finding that is not an expiry warning before one that is, then the longest firing first, then by ID. An expiry finding is one whose check has the category `expiry` (`account-003`, `account-004`, `server-016`; the limit checks `account-001` and `account-002` rank normally), and the API marks it `Finding.expiry`, so the Overview's cause cards rank a warning card of expiries only after the other warning cards. The owner decided on 2026-10-27: "between findings of the same severity, the headline prefers any finding that is not an expiry warning". Expiry stays a warning at 14 days and alerts as before, as the option the owner chose described. The session that built it read the rest, and the owner confirmed that reading on 2026-10-27: the rule also orders the Findings list, the findings of a server, stream or consumer page and the Overview's cause cards, not the headline alone; and since the owner's words speak of expiry warnings, a critical expiry (expired, or within 3 days) ranks as any critical finding, longest firing first. The status timeline orders its check rows by status, severity and code, without this rank: it lists every check of the range, and names no headline.

A finding's `since` is when nats-lens first saw it; `condition_since` is when the condition began, where the check knows it, and is unset otherwise, so a finding raised at the first epoch after nats-lens started does not read as a fresh problem. `GetLensInfo.history_start` is the start of the oldest stored epoch, and the finding page says when a finding was first seen at the start of that history.

A finding's state is flapping when the engine marks it flapping, changed when it fires and its last transition changed the severity, else firing or resolved. A range that ends more than one interval before now is a past range: its findings are rebuilt from `finding_transitions` as they stood at its end (state, severity, detail, value and cause from the newest transition before the end, since from the start of that episode, flapping from the hour before, mutes in force at the end), so a finding that fired, resolved and fired again keeps its earlier episode, and the statuses for that range use those findings. A live range that ages past that point switches once from the current state to the state at its end. A current range reads the findings table and the mutes in force now. The tally's resolved count is the resolve transitions of the 24 hours before the range's end. The value carries the header's `value_name` and `value_basis`; related configuration is the finding's own map with the header's `related_config` keys highlighted; the cause is the stored event the check named.

A finding event's summary is "<entity>: <detail>", and for a resolve "resolved: <entity>. Last failing result: <detail>". A finding event carries the transition, the finding as it is now and the check's name in its type; an event a finding names as its cause lists that finding as raised.

### Timeline and series

The status timeline takes its findings from the transitions in the range and the last one before it, and aggregates per check and bucket in SQL: one row per check that ran in the range (with an entity, one per finding of the entity, and with `include_ok` one for each check of the entity's type). A cell is the worst state of the epochs in the bucket whose run was ok: a firing finding's severity; muted when the findings firing then were under a mute in force at that run; ok when none fired; no data when the check did not run ok in any epoch of the bucket. `now` is the newest run's state with the mutes in force now. The event lane reads the NATS events and the finding transitions with a limit of 1000 each (`nats_truncated`, `finding_truncated`), so a burst of findings cannot push the NATS events out. The Kubernetes lane reads the newest 1000 Kubernetes events of the range (`kubernetes_truncated`).

`GetTimeSeries` metric IDs are `<scope>.<measure>`; the scope `cluster` takes no entity, `server`, `stream` and `consumer` take one of that type. Byte rates (`server.in_bytes_rate`, `server.out_bytes_rate` and their `cluster.` sums) come from the VARZ byte counters, and `stream.msgs_rate` from the increase of the leader's last sequence. The step is the range divided by `max_points`, rounded up to seconds and never below the collection interval. Buckets are aligned to the Unix epoch, so the first may start before the range and hold only its part, and a series can have `max_points + 1` points. Counts (servers up, connections, consumers, messages) take the last value of each bucket, so they stay whole numbers, with the bucket's lowest and highest value in the point's `low` and `high`; other gauges are averaged per bucket, counter rates are computed per server process, and slow consumer increases are summed. A rate is not computed across a gap of more than three intervals between two epochs (a collector restart), so the increase over the gap is never one sample. An overview tile shows its chart's last point, so the number and the chart use the same reduction, and the chart's range includes the value (the JetStream storage tile, whose value is the servers' newest report, widens the range to it). This replaces the earlier rule that a tile shows the newest epoch's value. The first epoch of a restarted server, and the first after a collection gap, has no rate, so the cluster rates dip for one epoch at every restart; this is a gap in the data, not a drop in traffic.

`cluster.cpu_percent` and `cluster.mem_bytes` are bands: per epoch the median (`quantile_cont`), lowest and highest server that reported the number. A bucket's value is the mean of its medians, and its `low` and `high` are the lowest and highest server value of any epoch in it, an envelope, so a spike stays visible however wide the step; the series' `min` and `max` are the smallest `low` and largest `high`, and a band tile's range track uses them. `top` is the server with the highest mean over the range and `top_points` its `server.` series in the same buckets, means per bucket, so the line lies inside the band. Counts of streams (not `KV_` or `OBJ_`), KV buckets, object stores and assets need a JSZ reply from every server that answered in the epoch, and accounts an ACCSTATZ reply from each, so a partial answer has no point rather than a dip; an account's streams make it active only when JSZ is complete too, else its connections alone count, so a system without JetStream still has the series. `cluster.accounts` leaves out the system account. A server that does not answer at all is not observed, so the R1 streams it holds drop out of `cluster.streams`, the bucket counts and the asset counts for that epoch, with no gap to show it; the complete-reply rule covers only servers that answered something. `cluster.assets_replicated` and `cluster.assets_single` count streams and durable consumers (ephemeral consumers come and go and are left out) by configured replicas, the largest count when servers disagree, and a consumer's replicas 0 as its stream's. `cluster.meta_leader_changes` takes the meta leader that more than half of the expected servers report (the answering servers when none is expected); a tie or a lone stale answer leaves the epoch without a leader, which is no change. It counts a change from the last epoch that had a leader, also across a collection gap, since the leader did change. `consumer.delivered_rate` reads the leader's row only, with no fallback to the highest follower, computes the increase per leading server and creation time, so a leader move or a recreated consumer starts again without a rate, and keeps the gap rule. `server.slow_consumers` and `cluster.slow_consumers` keep the gap rule too, so their sums agree, and neither counts a restarted process's first epoch. A cluster metric requested with an entity is `invalid_argument`; before it was read for the system silently.

### Overview tiles, placement and delivery rates

`GetOverview` returns nine tiles in a fixed order: `servers`, `meta_leader`, `streams`, `kv`, `object_stores`, `consumers`, `accounts`, `clients`, `storage`, replacing `connections`, `slow_consumers`, `js_storage` and `msgs_rate`; message rates move to the trends. Each carries a one-sentence `description` for its tooltip, kept in one table (`api.TileDescriptions`) for the store and the demo. A count tile's value is its series' last point, as before. The meta leader tile's `value` is the number of leader changes in the range (the sum of `cluster.meta_leader_changes`) and `value_text` the leader's name, by the series' rule: more than half of the expected servers, else empty. Streams counts replicated streams (more than one configured replica) rather than R3, so a five-node system's R5 streams count; KV counts the R1 buckets. A stream lags when its leader reports a replica not current. Consumers' "behind" counts firing `consumer-002` findings. Clients counts applications as distinct connection names up to an `@`, tooling connections left out by the client checks' rule, and the slow consumer events summed over the range; its value stays the servers' connection count, nats-lens's own included, so it matches its chart. The accounts subtitle names the account other than the system account with the most connections, counted as the Accounts page and `account-001` count them: clients plus the leaf nodes of the server process that holds the most (`checks.AccountConnectionsSQL` in the store, `api.BusiestAccount` over the page's facts in the demo), the first by name of a tie, so the tile names the account the page lists first (proposed, not yet confirmed). Storage's growth is the Theil-Sen slope of the summed `js_storage` over the range, with the stream growth's 6-hour minimum.

`StreamSummary.placement`, and a KV bucket's or object store's, comes from one rule (`placementOf`): one entry per replica, the leader first, the rest by server name, so the leader stands out at the start of the row. In order: one `LEADER`, the first by name of the servers that claim the lead, the others treated as followers; without a leader row, `UNSPECIFIED`, or `DISAGREES` when the reporting servers' non-empty config hashes differ; listed by the leader as offline, `OFFLINE`; reporting nothing itself, `MISSING`; not listed by the leader, `DISAGREES`; `current` false, or a lag with `current` unknown, `BEHIND`, whatever config hash it still holds, since a follower catching up keeps the old one; a config hash other than the leader's (both non-empty), `DISAGREES`; `current` true, `IN_SYNC`; anything else `UNSPECIFIED`, as an unknown `current` is never read as false. Configured replicas beyond the servers named are `MISSING` with no server, for buckets too. A "lagging" count on the overview counts the streams with a `BEHIND` square. Creation times are not compared here; the disagreement views show them.

`ConsumerSummary.delivered_per_second` is the leader's `delivered_consumer_seq` increase per second between the first and last leader rows of the newest run (leading server and creation time, as `consumer.delivered_rate` counts runs) inside the 15 minutes before the range's end, and is unset with fewer than two such rows or a decrease. `ListConsumers` sorts by it with `CONSUMER_SORT_DELIVERED_RATE` (highest first, unset last, ties by key) and keeps the first `limit`; zero or less means all, as the handler does not validate it. The demo takes the mean of its `consumer.delivered_rate` series over the same 15 minutes, and derives its placement from the stream's peers by the store's rule (leader first peer, a server that does not answer offline, a named follower behind, disagreeing or missing, every square unknown without a leader); `example-global`'s `search-index` has its `nats-ap-1` replica 420 entries behind, not current, below `stream-003`'s 1000, so the demo shows a BEHIND square and one lagging stream without a finding.

### Paging and limits

Findings and connections page by offset; events page by time and ID and mutes by ID (newest first), so new events and mutes do not shift the pages. Folded events page by the time and ID of each row's newest event, and the token keeps the highest event ID of the first page: later pages leave out newer events, so a row that gains an event cannot cross the page boundary. A connection page token keeps the epoch of the first page; once that epoch is swept, the token is refused with failed_precondition. A token is only valid with the same filters.

A request or response message is at most 1 MiB; a `GetReplay` spans at most 24 hours and returns at most 200 steps between A and B, 10 after B, 10 evidence and 50 entities per step and 200 gone assets; a `GetTopology` lists at most 500 leaf node sites and counts drops over at most the 24 hours before its epoch; a `GetAccountsAndAuth` lists at most 500 accounts, 100 failed-login groups (over the 24 hours before its epoch) and 100 expiring rows (expired, or expiring within 30 days of its epoch), each with its total; a `GetCapacity` lists at most 500 streams with their total; a `GetSubjects` lists at most 1,000 rows with their total, names at most 3 connections per row and lists at most 20 subjects per stream row, counting the rest in `more_patterns`; this bounds the count, not the bytes, so 1,000 rows of 20 subjects pass the limit once subjects average about 48 bytes or more (30 subjects of 64 bytes each made 1,357,022 bytes), and a row's `overlaps` list is not capped, and a `MatchSubject` subject is at most 255 bytes; a `GetMicroServices` lists at most 200 services, 100 endpoints and 100 instances per service with their totals, and names at most 3 connections per service; each call has 30 seconds in the provider, a `GetTimeSeriesBatch` call 40 seconds with 30 per query, and the web client's 45-second call timeout bounds every call it makes; filter lists hold at most 10 states, severities or sources and 50 kinds; the timeline holds at most 2000 buckets, counting a partial last one. An events histogram holds at most 120 buckets. The HTTP server has read, header and idle timeouts, a write timeout of the longest call's timeout (the batch's 40 seconds) plus 15 seconds, and a 64 KiB header limit. A panic in a call becomes an internal error and is logged with its stack.

### Mutes

A mute covers a check (`^[a-z]+-\d{3}$`), or a check for one entity of a known type; it needs a reason (at most 1000 characters) and an expiry between one minute and 90 days ahead, truncated to seconds. Lifted and expired mutes stay as history and are not swept by retention. The handler checks every rule before the store sees the row, so a row the table's constraints still reject is a server fault: internal, with the database's text only in the log. A mute call waits for the store's write lock only as long as its context allows.

### Accepted findings

An acceptance is a mute with `accepted` set (`MuteFindingRequest.accept`, migration `0031_accepted_findings`): it records one entity's finding as by design. It needs an entity with a key (the system entity is refused, as it has none), a reason as a mute does, and a review date as its expiry, between one day and 365 days ahead (`MaxAcceptLength`). The rule is checked in Go, not by a table constraint. Every reader of mutes reads an accepted row as a mute in force with nothing of its own: the findings list and `Finding.mute`, the tally and the Overview status, the Fleet badges, the status timeline's SQL, `/metrics` and the archive's `mute_changes`. Lifting is `UnmuteFinding`; `ListMutes` lists acceptances with the mutes. When several mutes cover one firing finding, one for its entity wins over one for the whole check, an acceptance wins over a plain mute of the same entity (so the finding reads as accepted), and otherwise the newest wins. At its review date an acceptance runs out as a mute does, and the finding counts again if it still fires.

The server records the entity's growth at acceptance in `growth_per_day`; the request has no field for it. For a stream it is the leader's bytes (any replica's in an epoch without a leader row), for a server its `js_storage` by server name, read in one SQL query (`Store.GrowthPoints`) as bucket medians 48 minutes wide (30 a day, so the grid falls on the same times every day and week; the collect interval when that is longer), over two spans only: the day before now and the day a week before that, each an hour wider (`api.AcceptGrowthSpans`). The rate is the week's growth (`api.WeeklyGrowth`): for each point p of the last day, the value a week earlier is interpolated between the two points around it, never across a gap of more than three bucket widths, and the rate is the median of (v(p) − v(p − 7 days)) / 7. Any pattern that repeats every day or every week (business hours, weekdays only, a cleanup every Sunday) adds the same to every difference and cancels; noise is damped by the median over a day of points. It needs the points with a partner to cover two thirds of the last day, a stretch between two of them (or the day's ends) counting only when it is at most 2.6 bucket widths, and to number at least half the buckets a full day has (day divided by the width). So it needs 8 days of history, the last day collected for at least two thirds of its length with no more than one bucket in a row missing, and at least half of that day's buckets: after an outage over most of the day, or with a collector that keeps one bucket in three, there is no rate, rather than one that a few pairs decide. Coverage rather than a full count, because at a collect interval of 48 minutes or more each bucket is one interval wide, and epochs within jitter of the bucket grid put two epochs in one bucket and none in the next, which loses no data but loses a point; without a missing epoch two points are then at most 2.5 widths apart plus half the jitter, hence 2.6. For a younger entity nothing is recorded at acceptance, and the review records the rate as the baseline the first time it can be measured, ending nothing that time (a conditional update, so it cannot race with a person lifting the acceptance). Other entity types record none and are not reviewed. The review reads back 8 days and an hour (`api.AcceptRetention`); with a shorter `retention` the sweep has removed that data, so acceptances record no growth and never end early, only at their review date: nats-lens logs a warning at start, and the finding page says so from `GetLensInfo`'s retention (the default retention is 14 days).

This is not the rule of the Streams page and the Capacity page's "/day" (`RobustPerDay`, Theil-Sen over the page's range). Theil-Sen over one 24-hour window reads a stream that grows 3 MiB an hour from 09:00 to 17:00 as +33.7 MiB/day at 01:00 and +4.2 MiB/day at 12:00, and a day-over-day median still followed weekly patterns and purges, so a review at every epoch ended acceptances whose growth never changed. The numbers can therefore differ; the end reason says what it measured.

After each successful check run the runner reviews the acceptances of streams and servers in force at the epoch's time (`runner.ReviewAcceptances`): one query reads them, one reads the two spans of all their entities, and each one whose week's growth now differs from the recorded one by more than half of the larger of the recorded rate's size and 1 MiB per day is ended: `unmuted_at` the epoch's time, `unmuted_by` `nats-lens`, `end_reason` "growth changed from +10 MiB/day to +16 MiB/day over the last 7 days (+92 MiB in the last day)". The week's figure is the rate the review compared; the last day's change shows the new rate of a change that began recently. The 1 MiB floor keeps a bucket accepted at about +0 from returning on a few KiB of change. A lasting change ends an acceptance once the week's growth has moved past the half-way mark: within a day for +10 to +100 MiB/day, about two days for +10 to +30, six days for +10 to +16. A purge or a restore changes the week's net growth and does end the acceptance, within a day: the finding returns, and a person can accept it again. A growth that cannot be measured now (too little history, an outage over more than a third of the day, the entity gone) changes nothing. The review never touches a plain mute, an acceptance created after the epoch started, or one already ended, so it ends each acceptance at most once. With 200 acceptances of streams collected every 30 seconds for 8.5 days, a review took about 130 ms. A baseline the review writes counts as a mute change (`muteChanges` counts acceptances with a growth), so the newest hour is exported again with it; a rebuild keeps, among copies not lifted, the one with the growth. The demo keeps `accept`, a growth (for now its scenario's `RobustPerDay` over 8 days, until the demo's acceptances are reworked) and `end_reason`, and does not simulate the review.

### Health and metrics

`/healthz` answers while the process serves; it is the liveness probe and the load balancer's health check. `/readyz` answers ok once every system's store is open and the API serves; the API starts after the database is open, so a pod that rebuilds its database gets no traffic, and the start probe allows ten minutes for that. Readiness does not follow collection: with one replica a not-ready pod leaves the load balancer, and the UI would vanish exactly when NATS is down. A stopped collector shows as `collecting` false in the API's freshness, which the header shows as "not collecting since HH:MM", and through `nats_lens_last_epoch_age_seconds` and its alert rule. The collector's own connection is dialled again when nats.go closes it for good, with the event connections' backoff.

`/metrics` on the API listener exports each firing finding as three series of one identity (`system`, `code`, `entity_type`, `entity_key`): `nats_lens_finding` with a `muted` label, `nats_lens_finding_severity` (1 to 3) and `nats_lens_finding_flapping`, so that a change of severity does not start a new series. A mute does start a new `nats_lens_finding` series, as `muted` is its label; the `_severity`, `_flapping` and `_by_check` families keep their identity. The three series are capped at 50 unmuted entities per check (the worst, then by entity key, so the set is stable); muted findings are always exported and do not count against the cap. Beside them: per-check counts and highest severity without severity labels, counts by severity and of muted findings, and the health of the collector and the checks, including epochs without check runs. Every sample carries `system` as its first label; the handler collects the samples of every system by family and writes each family's HELP and TYPE once. Each system is read in parallel into an exposition of its own, within `metrics_timeout` (8 seconds, below the usual 10-second Prometheus `scrape_timeout`) and never twice at once, a panic counting as a failure, and merged only when it succeeded, so a failure halfway leaves no partial families; `nats_lens_system_scrape_success` says per system whether it was read, and the scrape answers 500 only when every system failed. An empty system ID is refused when the registry is built and when an exposition is made, so no sample goes without the label. A mute makes alert rules on the finding series stop matching.

Findings can reach [notification channels](#notifications) directly. Separately, a Prometheus scrapes `/metrics` (on GKE, Managed Prometheus through a PodMonitoring), and its alert rules or Cloud Monitoring PromQL alert policies evaluate the findings; the README gives example rules.

### Demo

`natslens demo` serves three fake systems without NATS or a database: `example-prod`, the default, with the reference mockup's scenario (a GKE node upgrade); `example-global`, 24 servers in clusters `eu`, `us` and `ap` joined by gateways after a node upgrade left one server down, with one store 71% full and two servers on an older version; and `example-staging`, whose collector connection closed three hours ago after its credentials were rejected, so its data ends then. Each is a `scenario` value in `internal/api/fake` that the same RPC code serves; a scenario's times are written in a fixed frame and shifted to now unless `-fixed`, which keeps them at 2026-10-17 14:30 UTC (`fake.FixedNow`), the provider's `Now()` and `GetLensInfo`'s `now`. It uses the same event kinds as the real capture, and is the fixture for handler tests and for building the UI without a cluster. For Replay, `example-global`'s pool upgrade is a story: lame duck announcements, leader elections that follow each restart, assets held before and after each restart, clients reconnecting to each new process, two durables gone without a delete event with their `consumer-013` findings, and a bucket gone with the server that held it. The demo builds `ReplayFacts` from the scenario and `FinishReplay` words them as for the store. Its pages agree with its events: the leaders come from a leaders' history built once per scenario, in which an asset starts with its initial leader (example-prod's spread over the replicas), changes lead only at an election and has none while its leader is down; where the scenario writes no election within 90 seconds the demo elects the first answering replica (a consumer its stream's new leader) and writes the election as an event; a single-replica asset has no election and leads again with its server; placement, servers, the meta tile and Replay's leaders at A read that history, with `leader_since` the election or the leader's process start; durables that went are a stream's `vanished` list, listed for ranges before they went and read as gone assets; the Kubernetes lanes and windows come from its Kubernetes events by the store's rules (`api.K8sLaneKinds`, `api.DeriveK8sWindows`), and the NATS lane draws the store's kinds (`api.NATSLaneKinds`); node events carry `node`, `pool` and `kubelet_version`, each node is cordoned, drained as its NATS pod leaves, upgraded and uncordoned, and a node pool's own report is a `k8s.event` because it names no node. For Topology each scenario has a `linkSpec` (`internal/api/fake/links.go`): routes, gateway round trips and reconnects, the servers that stopped, and leaf node sites with their reconnects and outages; the demo builds `TopologyFacts` for the range's epoch, counts the drops of the collections of the 24 hours before with `api.CountTopologyDrops`, and `FinishTopology` finishes them as for the store. A gateway or site whose server stops moves to the next server of the cluster that never stops, a move the reporter sees as a drop for a gateway and the stopped hub does not count for a site. The Server page reads the same links at the range's epoch (a stopped server's last): the pooled and pinned routes with the same round trips, and the leaf node sites on each server; `example-global`'s account connection events are worded as the capture words them, with the server's leaf nodes in the total. Findings keep their present state in every range: a past range lists a finding resolved later as resolved (a leftover). The collecting demo systems report the collection state demo; `example-global` reports the cluster name `eu`, its meta leader's, as a system reports one of its servers' cluster names. For Accounts and auth each scenario has an `authSpec` (`internal/api/fake/accounts_scenarios.go`): the stream account's lookup, the other accounts, the clients that fail to log in, the servers' listener certificates and the user JWTs of its connections; the demo builds `AccountsFacts` for the range's epoch and `FinishAccounts` finishes them as for the store. `example-global` is in operator mode with APP, the system account SYS and an idle SUPPLIERS whose identifier is an account public key; APP and SYS keep their names as identifiers, as they appear on every other page. Its failed logins are `client.auth_error` events that the Events page lists too, each on a server up at its time, and the page groups them from those events; the revoked user `scale-terminal-07` is not a client the demo has connected; a server down at the epoch (`nats-us-4`) keeps its certificates from its last collection, with `seen_at`; its three pos-terminal connections are in the connections list. `example-prod` is in config mode with APP looked up and certificates more than 30 days out; `example-staging`'s APP was never looked up and its servers report no certificates. For Capacity a stream's `streamSpec` holds its retention, storage, limits, mirror, sources and the age of its oldest message, and a bucket's limits come from its `bucketSpec` (TTL as `max_age`, history as `max_msgs_per_subject`, discard new); the demo builds `CapacityFacts` for the range's epoch with growth by the store's rule over its series, and `FinishCapacity` finishes them as for the store. Every `stream-005` of the demo is written from these specs as the check writes it (`unboundedFinding`), and a test checks that the storage findings, mutes and acceptances agree with the specs and with the series: `stream-005` fires on exactly the unbounded streams the inventory does not declare, an acceptance recorded its entity's growth then, and one nats-lens ended was ended when the review's rule (`api.WeeklyGrowth` over the bucket's series) finds the change and at no collection of the day before, the helper reading the series as the runner reads the store (each bucket's epochs, their middle, the last bucket cut at the review time), with the end reason the review writes, and has its finding firing again. ## Kubernetes

The watcher (optional, `kubernetes.enabled`, in-cluster and read-only) reads `events.k8s.io/v1` Events only: the core `v1` Events API serves the same objects, so watching both would double the traffic. It also watches the NATS pods (by label selector) in the same namespaces, the nodes, and the node Events in `default`, where the API server files them.

- Every kind has one origin, so that one change is stored once. State changes (pod scheduled, ready, not ready, restarted, evicted, terminating, deleted; node added, cordoned, uncordoned, ready, not ready, deleted, kubelet version changed) come from the pod and node watches; the kubelet's and controllers' reports (killing, started, unhealthy, back-off, failed scheduling, preempted, a node Event whose reason names an upgrade) from the Events. An eviction is recorded once, from the `DisruptionTarget` condition or the `Evicted` Event, whichever comes first. Kinds carry a `k8s.` prefix (`k8s.pod.killing`, `k8s.node.drained`).
- `k8s.node.drained` is derived: a NATS pod evicted, terminated or killed on a cordoned node, recorded once per cordon. A cordon is `spec.unschedulable` or the cluster autoscaler's `ToBeDeletedByClusterAutoscaler` taint, which drains a node without setting it unschedulable. A cordon seen after a NATS pod on the node was already evicted or terminating is a drain too, as the watches do not order the two; the drained event carries the cordon's cause.
- Node changes are kept for nodes that run or ran a NATS pod within the last hour, and for nodes added within 15 minutes of a drain or upgrade, as a surge upgrade adds the new node before it drains the old one. Keeping every node of a pool that held a NATS node is `kubernetes.pool_nodes`, off by default: on GKE Autopilot the autoscaler's few pools hold every workload, and their churn would bury the upgrade.
- Pod Events of a NATS pod are stored with its server name (`kubernetes.server_name`), except routine ones (`Scheduled`, `Pulling`, `Pulled`, `Created`) and those of other containers (the config reloader). Events of other pods are stored only as warnings, kills, evictions and preemptions, without a server name.
- Each Event occurrence count is stored once: the watcher remembers the highest count per UID for three hours and is seeded from the store at start, so a relist or a restart of natslens does not store the Events again. A Kubernetes Event is one row per UID: a higher count updates the row stored within the last three hours (count, note, summary and receive time become the latest; `time` stays the first occurrence and `raw.first_seen` and `raw.last_seen` record both) instead of adding a row. The new receive time moves the row to the hour of its latest occurrence, so the archive exports both hours again by their event counts; an exported hour left without rows is exported again empty.
- Watches resume from the last resource version seen (bookmarks included). An expired version (410) means a relist, whose differences are recorded timed when noticed; it is not a gap. A list or watch failing for `gap_after` (30s) is recorded as `collector.k8s_not_watching`, its recovery as `collector.k8s_gap` with the span. A watch the server ends without an error within a second counts as a failure, and the next one opens a second later at the soonest; a failure ends when a watch opens, not at the first event, so a quiet namespace after a short failure is no gap. Lists are paged by 500 objects, at most 20 pages; attempts wait 1 second doubling to a minute.
- At start the watcher records a `collector.k8s_gap` from the newer of the last stored Kubernetes event and the last epoch, when longer than `gap_after`, and compares its first lists with the state the stored events last gave each NATS pod (ready, present) and node (cordoned, present), recording the differences as observed at start.
- The timeline's Kubernetes lane shows node cordons, drains, readiness, upgrades and deletions, the NATS pods' stops, starts and readiness, the watch gaps, and, as warnings, the failed scheduling, crash loops (`BackOff`, `CrashLoopBackOff`) and OOM kills of pods that are NATS clients: a pod whose name follows "@" in a connection name seen from an hour before the range, or one `kubernetes.client_pods` matches. The pod names are read once per collect interval per range and kept for up to 8 ranges (least recently used dropped), not on every lane request. No check reads them yet. `k8s.pod.oom_killed` comes from the pod watch for NATS pods (a restart whose last termination is `OOMKilled`); client pods are not watched, so for them it comes only from an Event with reason `OOMKilled` or `OOMKilling`, which kubelets do not send for pods (their `OOMKilling` is a Node Event). The retained Events of the development cluster it was tried on held no OOM, back-off or failed-scheduling Event, so the client path is untested on a real cluster; with a server entity only that server's pods, with any other entity the whole lane, as a drain is context for every stream. The NATS lane does not hold Kubernetes events.
- A node upgrade window opens at a drain or an upgrade, not at a cordon alone (the autoscaler cordons too), and takes in every following node or NATS pod event within 15 minutes of the one before; it ends at the last one, normally the last node or pod back to ready. A window without a drain or a NATS pod event is not shown. Windows are derived when read, from the newest 5000 events up to 12 hours before the range, not stored. One window covers all pools; its label is "Node upgrade" with upgrade evidence (an upgrade event, or nodes of different kubelet versions), "GKE node upgrade" when a node in it also carries GKE's `cloud.google.com/gke-nodepool` label, "Node removed by the autoscaler" when every drain in it was the autoscaler's (a NATS disruption all the same), else "Node drain".

## Deployment

- One replica with the `Recreate` strategy, since DuckDB has one writer, and a PVC for the database and the archive until a bucket destination exists. The `gke-iap` example gives the PVC `argocd.argoproj.io/sync-options: Delete=false,Prune=false`, so that Argo CD never deletes the history.
- GKE Autopilot: the pod carries `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`, and its CPU limit equals its request, as Autopilot requires both. A preferred pod anti-affinity (weight 100) keeps it off nodes with a NATS server pod when another node fits, so a drain of that node does not take the observer away; a node pool of its own cannot be had on Autopilot, where pools are the autoscaler's.
- Its own namespace `nats-lens`, with list-and-watch Roles in the NATS namespace (Events, pods; `nats` in the base) and `default` (node Events) and a ClusterRole for nodes.
- Distroless `cc` image as user 65532 with a read-only root filesystem and an `emptyDir` on `/tmp`; 30 seconds to stop. The Dockerfile's Node and Go stages run on the build platform and the Go stage cross-compiles for `TARGETARCH` with Debian's gcc cross toolchain and cgo for DuckDB, so an amd64 image builds on an arm64 host without QEMU. Images go to `registry.example.com/nats-lens/natslens`.
- `k8s/base` is provider-neutral; `k8s/components/gke-iap` adds the GKE pieces, and `k8s/examples/` holds two overlays to copy: `basic` (port-forward only) and `gke-iap`. A deployment keeps its own overlay, with its image and its whole `natslens.yaml`, outside this repository.
- The NATS credentials are two Secrets the overlay provides, `natslens-nats-system` and `natslens-nats-app`, created by hand or synced from a secret store. The NATS users are scoped to the subjects natslens uses (README, NATS permissions); tests show the grants are enough.
- In the `gke-iap` example an HTTPRoute attaches to an existing Gateway; a GCPBackendPolicy turns IAP on and a HealthCheckPolicy points the load balancer at `/healthz`.
- A NetworkPolicy admits port 8080 only from Google's load balancer ranges and from Managed Prometheus (`gke-gmp-system`); a PodMonitoring scrapes `/metrics`.
- The image digest and the IAP audience are filled per deployment; the `gke-iap` example carries placeholders that the API server and natslens reject.

## Security

- No authentication of its own; IAP decides who may pass. natslens refuses to listen beyond loopback without `iap_audience` unless `allow_unauthenticated: true`, and an `iap_audience` must have the backend service form.
- With `iap_audience` set, mute and unmute need the signed `X-Goog-IAP-JWT-Assertion`. It is verified (ES256 against Google's IAP keys, fetched and cached for an hour, refetched at most once a minute for an unknown key, failed fetches included, one fetch at a time and without holding up callers whose key is cached; while refreshes fail, the cached keys stay trusted however old they are; issuer `https://cloud.google.com/iap`, the audience, exp and iat with 30 seconds of skew), and its email is recorded as the user. A call without a valid assertion is unauthenticated. Without `iap_audience` both IAP headers are ignored and the request names the user. Reads never need an assertion.
- Host allowlist: the API answers only requests whose Host is in `allowed_hosts`; without the setting that is localhost, 127.0.0.1 and ::1 when the listen address is a loopback one (against DNS rebinding from a web page), and any host otherwise. `/healthz` answers every host. On a loopback listener the allowlist applies to `/metrics`; on any other listener `/metrics` is exempt, because Prometheus scrapes by the pod's address, and that listener must stay inside the cluster.
- Every UI and API response carries `Content-Security-Policy`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer`. The policy is `default-src 'self'`; `script-src` and `style-src` are `'self'` plus the sha256 hash of each inline script and style of the embedded `index.html`, computed at start so they follow every build; `img-src 'self' data:` (the favicon); `object-src 'none'`, `base-uri 'none'`, `form-action 'self'` and `frame-ancestors 'none'`. No `unsafe-inline`.
- Credentials are never logged; the password has no flag, so it never shows in the process list. User JWTs are removed from stored event payloads at any depth.
- Supply chain: base images are pinned by digest; the web tree has an `.npmrc` with a min-release-age cooldown of 7 days; `make vuln` runs govulncheck when it is installed.

## Bounded history sample boundaries

Proposed, not yet confirmed: bounded Data history uses can establish their lower
window boundary with actual collections on either side, each within one configured
collection interval. The interval must be positive and shorter than the window;
the window must contain two distinct samples and end at the latest stored collection.
The separate predecessor is never added to the displayed in-window sample span.
This avoids permanently short rolling windows after a collection phase change
without crediting calendar age or elapsed time after collection stops. It describes
global sample availability, including possible internal gaps, rather than continuous
coverage or entity algorithm eligibility. Growth retains its strict measured span.

## Slow-route finding (proposed, not yet confirmed)

`server-025` is an operational warning on each stable server name touched by a slow pair. Both endpoints receive it: RTT alone cannot assign responsibility for a slow link. The detail names peers, current RTTs and the two collection numbers; the numeric value counts slow pairs. These mapping, severity and evidence choices are proposed, not yet confirmed.

`internal/routehealth` owns the pure pairing and classifier extracted from Topology, including unknown/zero RTT handling and the intersection of two independently classified collections. Its shared stored-route reader resolves captured peer names before process names and IDs. Pair identity remains Topology's stable name pair, not a route ID or a process counter. Two actual RTT observations across a process replacement remain eligible; a missing observation cannot be carried forward. Unknown reporting clusters are placed by incoming named routes as on Topology. The previous route-bearing collection must start before the current collection and within three configured intervals; an unknown interval supplies no previous collection. These eligibility and identity choices are proposed, not yet confirmed.

The engine reads current route rows, selects one previous collection and reads its rows, using its existing connection and per-check timeout inside the rotating epoch budget. Classification checks cancellation between pair-reference scans. Query count is independent of server count. The live collector and offline checks command supply the configured interval; no migration, proto change or NATS request is added. The existing demo scenarios retain their Topology behavior; no synthetic slow-route findings are added to their fixed finding stories.

## Leaf-health evidence retention (proposed, not yet confirmed)

`server-026` retains uncertain evidence only from its own latest successful execution before the requested epoch, with `updated_epoch` strictly before that epoch. Failed, budget-skipped and unapplied executions leave this continuity intact. Disabling resolves the finding and resets it. These rules match the approved churn execution guard.

Each identity's last-observation timestamp in the persisted finding detail supplies durable expiry proof. Carry preserves that timestamp, including fractional seconds, across evaluations and store reopen. It expires each identity independently after 24 hours; fresh confirmed evidence can join without extending another identity's age. The parser accepts only the code-owned evidence format and fails the check on unknown evidence, preserving existing state instead of silently resolving it. This uses the existing detail field without changing migrations, the API, or configuration metadata. The format and per-identity retention are proposed, not yet confirmed.

Expiry ends a warning because recent evidence is unavailable; it does not establish observed recovery. With eligible coverage, the original rules still clear absence on reconnect and clear repeated drops below three in the rolling hour. During uncertain coverage, the retained last-observation window bounds either kind of earlier evidence. This distinction is proposed, not yet confirmed.


## Fatal database containment (proposed, not yet confirmed)

Proposed, not yet confirmed: each store guards its DuckDB connector, shared by
all SQL connections to that engine. A wrapped `*duckdb.Error` with
`ErrorTypeFatal` latches the first failure. Further engine operations are refused;
cleanup can still release native resources. Calls admitted before the failure
can unwind, and calls with contexts receive cancellation. This boundary covers
store-backed collection, checks, events, notifications, archive work, and API
queries, including prepared statements and transaction commits.

The affected system cancels its workers with a local shutdown deadline. Other
systems keep their own engines and workers; a failed system cannot consume their
later shutdown grace. The API remains available until external shutdown, even
when every system failed. Process readiness fails if any engine failed, while
liveness continues. The existing closed collection state carries the bounded
failure in system summaries, without a new protobuf field. These policy choices
are proposed, not yet confirmed.

Fatal diagnostics keep an allowlisted mechanism summary and the operation stage.
Arbitrary engine text, wrapping text, row chunks, SQL, and paths from diagnostics
are discarded. Classification survives through a sanitized typed cause. This
intentionally trades detailed diagnostics for bounded, secret-safe reporting.
Nonfatal errors retain their existing behavior.

Containment never reopens a failed engine, repairs data, changes indexes or
migrations, or upgrades DuckDB. A fatal error at open does not select the existing
automatic WAL-rebuild path. The disposable regression demonstrates one pinned
engine failure; it does not establish the cause of another database's failure.
[Upstream PR 25771](https://github.com/duckdb/duckdb/pull/25771) addresses shutdown
checkpoint prevention, not repair of existing index divergence. Dependency
upgrades and recovery require separate work.

Consumer replica degradation (`consumer-018`) uses the leader's peer facts in a single batch over the newest `min_epochs` collections. It requires stable identity, leader, membership, effective replica count, corroborating quorum reports and a surviving online quorum. Unknown observations hold an existing warning with a null value instead of certifying health. Severity warning, 3 collections, maximum gap 90 seconds and election/startup grace 2 minutes are proposed, not yet confirmed. No schema or collector change is required. NATS 2.15.0 defines leader lag as committed Raft entries not persisted by a peer; followers intentionally leave other followers noncurrent with zero lag ([raft.Peers](https://github.com/nats-io/nats-server/blob/v2.15.0/server/raft.go#L2447)). Cluster info also clears current after the lost-quorum activity interval and obtains offline from node information ([jetStream.clusterInfo](https://github.com/nats-io/nats-server/blob/v2.15.0/server/jetstream_cluster.go#L13384)).

## Overview tiles chart only a change (proposed, not yet confirmed)

An Overview tile draws its chart only when `tileChartReason` (`web/src/lib/tileChart.ts`) does not call it steady. It keeps the chart for a warning or critical status; a series without points; a missing bucket, judged on the step's grid from the Unix epoch that the store's `time_bucket` and the demo's `api.BucketStart` both use (the first bucket expected is the one holding the later of the range start and the history start, the last the one holding the range's end, one bucket earlier in a live range; two points more than 1.5 steps apart; the second series too); a collection gap in the range of a hatched kind other than before history, or of an unknown kind; or a change: a value that differs, a bucket's low or high that differs from the value, the series' min and max that differ (the storage tile widens them with the newest report), or for the meta leader a bucket with a change. Info and muted statuses do not keep a chart. While the gaps are not known (loading or failed), a tile with no change has no chart and its track row shows the chart history status ("History gaps loading", "History gaps unavailable") in place of "steady at N" (`MetricBox` `historyStatus`); the gaps load with the overview query (`Overview.tsx` asks for them under the charts' key), so a tile rarely changes height when they arrive.

A count series that takes each bucket's last value (`arg_max`) also fills the point's `low` and `high` with the bucket's lowest and highest epoch, in the store and in the demo, so a dip inside one bucket is seen. The series' `min` and `max` stay on the bucket values, which the Detailed trends, stream and server charts state beside lines that do not draw the edges; the Overview tile widens its own track with the points' `low` and `high` (`edgeRange`), so it reads 2 to 3 rather than "steady at 3". The fields keep their band meaning for band metrics, and summed counts and other gauges leave them unset.

Charts that remain use the `change` tone of `Sparkline`: neutral line and fill, the accent on changed segments, or, when more than half of a run's segments change, one accent dot on the newest point; a bucket gets a tick from its low to its high only when one of them lies beyond the line around it (below the lowest or above the highest of its own value and its neighbours' values, `hiddenMoves`) by at least a quarter of the span from the lowest to the highest value, lows and highs included, and by more than twice the median reach of the other buckets (`tickedMoves`), so a dip the line reaches, small moves and a count whose every bucket swings about as far draw no ticks, while an outage inside busy noise draws one. The chart scales to its values and the ticked lows and highs, so unticked noise does not squeeze the line; the track's ends take in every low and high. Its SVG overflows on every side but the left, so the newest-point dot stays whole while the first bucket, which can begin before the range, stays clipped. Warning and critical keep their severity colour. Steady tiles show their steady line and note under the heading.
