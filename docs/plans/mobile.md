# On call on the phone build plan

Working plan for On call on the phone (`docs/features/mobile.md`). The owner decided on 2026-11-05 to build it ("all good important points, lets implement"); every choice below was proposed by the planning session of 2026-11-05 and is not yet confirmed. When a task lands, its lasting content moves into `docs/features/mobile.md`, `docs/features/triage-and-mutes.md`, `docs/features/metrics-and-alerting.md`, `docs/features/navigation.md` and `docs/design.md`; this file then only tracks status.

Examples use the online shop of `inventory.example.yaml`, the demo's systems (`example-prod`, `example-global`, `example-staging`), `alice@example.com` as the person on call and `nats-lens.example.com` for the UI.

## Open questions for the owner

1. **Acknowledging is a record of its own, not a mute.** Proposed: an acknowledgement says who works on one finding's current episode, with a note and a quiet time; the finding stays on the Overview, in the tally and in the Findings badge, marked "acknowledged by alice@example.com". It ends when the finding resolves. A mute stays what it is: it hides a finding. Recommended: yes. Storing it as a kind of mute would make every reader of mutes (the tally, the status, the badges, the timeline's SQL, `/metrics`) hide it, which is the opposite of what acknowledging is for, and acceptances already took that path for a reason that does not hold here.
2. **"Quiet the alert" reaches Prometheus too.** Proposed: while an acknowledgement's quiet is in force, `/metrics` exports `nats_lens_finding_acknowledged` (1, the finding's identity labels), and the README's finding rules add `unless on(system, code, entity_type, entity_key) nats_lens_finding_acknowledged`; the notifications of `docs/plans/notifications.md` hold back reminders the same way. Recommended: yes; without it, "quiet for 2 hours" quiets only nats-lens's own channels, and a deployment that pages through Prometheus is paged again.
3. **The playbook link.** Proposed: `checks.remediation_file` accepts, beside the plain text it takes today, an entry `{text: …, playbook: https://…}`, and the card links that URL, with the first sentence of the remediation as its warning. Recommended: yes; deployments keep their playbooks outside the repository already (AGENTS.md), and the other choice, reading the first URL out of free text, breaks on the first remediation that cites a second URL.

## Rules for every step

- Read-only towards NATS. Acknowledging writes only to nats-lens's own database, as a mute does, with the same identity rule: the verified IAP user with `iap_audience`, else the name the request gives.
- One URL for a finding. A notification, a Prometheus annotation and every UI link open `/findings/<id>?system=<id>`; the phone layout is that page at phone width, not another route. The only new route resolves a finding from its labels (T3), for alert templates that cannot build the ID.
- The existing breakpoints: phone is 760 px and below (`web/src/styles/responsive.css`, `app-responsive.css`), tablet up to 1180 px. A page that renders a different tree on a phone uses one hook, `usePhone()` (`window.matchMedia("(max-width: 760px)")`), so CSS and script agree on one number.
- A value not observed is unset, never 0; the card says "not reported" rather than "0 of 3 online".
- Mutes apply when findings are read; so do acknowledgements, which are matched to the finding's current episode when read.
- `docs/design.md`, `docs/features/README.md` and the README are edited only by T4 (see "Order with the other phase 3 plans"); the other tasks record their departures here.

## T1 Acknowledgements: store, API, metrics and demo

- **Model.** An acknowledgement belongs to one finding and one episode of it (`findings.since_epoch` when it was made). It has a note (optional, at most 500 characters: on a phone "I'm on it" alone says something), who made it, when, and a quiet end: 30 minutes, 2 hours, or until resolved (no end). It is in force while the finding fires in that episode and nobody ended it; a new acknowledgement of the same episode ends the one before it (`replaced`), so "still on it, 1 more hour" is a new one. It is refused for a finding that is not firing (failed_precondition) or unknown (not_found).
- **Migration `0037_acknowledgements.sql`** (0035 is taken by `docs/plans/notifications.md` T2 and 0036 by its T3 delivery, both built first; migrations must be added in number order, as `natslens` applies only the files above the database's highest version and would skip a lower number added later; if another branch lands a migration first, both take the next free numbers before they merge, as neither will have been applied anywhere): table `acknowledgements` (`id` from `ack_seq`, `finding_id`, `check_code`, `entity_type`, `entity_key`, `since_epoch`, `note`, `acked_by`, `created_at`, `quiet_until` NULL for until resolved, `ended_at`, `ended_by`, `end_reason` (`released`, `replaced`)), comments on every column; and `archive_hours.ack_changes BIGINT` (NULL for hours exported before it).
- **Archive.** Written whole with every hour, as `mutes` is, and the newest hour exported again when the count of acknowledgements plus ended ones differs from `ack_changes`; a rebuild keeps each acknowledgement's newest copy (the ended one once ended). The implementer checks that a rebuild from Parquet written before 0037 still loads (`internal/store/archive.go`), and says how.
- **Retention.** An acknowledgement whose episode ended (the finding resolved, or fired again with a later `since_epoch`) or that was ended, longer ago than the oldest kept epoch, is swept (`internal/store/retention.go`).
- **API.** `AcknowledgeFinding(AcknowledgeFindingRequest) returns (AcknowledgeFindingResponse)` and `EndAcknowledgement(EndAcknowledgementRequest) returns (EndAcknowledgementResponse)` in `service.proto`. `AcknowledgeFindingRequest`: `system`, `finding_id`, `note`, `google.protobuf.Duration quiet_for` (30 minutes to 24 hours), `bool until_resolved`, `acked_by` (as `muted_by`). `EndAcknowledgementRequest`: `system`, `id`, `ended_by`. Message `Acknowledgement`: `id`, `finding_id`, `note`, `acked_by`, `created_at`, `quiet_until` (unset: until resolved), `bool quiet` (the quiet is in force now), `ended_at`, `ended_by`, `end_reason`. `Finding` gains `Acknowledgement acknowledgement = 20` and `FindingTally` gains `int32 acknowledged = 7` (firing findings with one in force; they stay counted where they are). The handler validates in Go (`normalizeAck` in `internal/api/normalize.go`), with the mute calls' identity path (`h.user`). `ListFindings` gains no filter in this version.
- **An event for the team.** Each acknowledgement is also written, in the same transaction, as an event of source `finding`, kind `finding.acknowledged`, summary "<entity>: acknowledged by alice@example.com: Upgrade in progress; watching nats-2", so it shows on the Events page, the timeline and the finding page's events. Not routine.
- **Metrics.** `nats_lens_finding_acknowledged` with the finding's identity labels, 1 while a quiet is in force, exported for the findings that have the three finding series (the same cap); `nats_lens_findings_acknowledged` counts them per system (`internal/api/metrics.go`, `storeprov/metrics.go`).
- **The design's sentence "The mute calls are the only writes"** becomes "The mute and acknowledgement calls are the only writes" (T4 writes it).
- **Demo.** `fake` keeps acknowledgements in memory as it keeps mutes. Seeded: in `example-prod`, `consumer-010` on `order-archive`'s `analytics-aggregator` (critical, firing since the node upgrade) acknowledged by `alice@example.com` with "Recreating the durable; the worker's drain fix is in review", quiet 2 hours; in `example-global`, an acknowledgement ended by a later one (`replaced`). `fake_test.go`'s counts change with it.
- **Conformance rows** (`apitest/conformance_oncall.go`, one line in `conformance.go`): a finding with an acknowledgement in force, quiet and not quiet; an ended one does not show on its finding; the tally's `acknowledged`; an acknowledgement of a resolved finding refused; both providers.
- **Tests.** Normalize: note of 501 characters, a quiet of 29 minutes and 25 hours, `until_resolved` with `quiet_for`; identity with and without IAP; a new episode leaves the old acknowledgement out; `replaced`; the event's summary; the metric only while quiet and its cap; the archive round trip and an old archive; the sweep. Store tests under a non-UTC `TZ`.

### Where T1 departed from this plan

Each point was decided in the session that built T1: proposed, not yet confirmed.

- **Migration `0037_acknowledgements.sql`, not 0036.** 0036 is the notification delivery migration of `docs/plans/notifications.md` T3, which reached `develop` first; the branch has `develop` merged, so 0036 is below it and the order is right. The runner applies only files numbered above the database's highest version, so 0037 must never merge before 0036.
- **`archive_hours.ack_changes` is a fingerprint, not a count:** `bit_xor(hash(id, ended_at)) >> 1` over the table. The retention sweep deletes acknowledgements, so a count of rows plus ended ones could fall and rise back between two exports and miss a change; the fingerprint changes with every acknowledgement made, ended or swept. Hours exported before 0037, and hours a rebuild loaded, have NULL, so the newest is exported again once.
- **The old archive check.** An archive written before 0037 has no `acknowledgements` files and a `state.json` without `max_ack_id` (the field is new in `archive.State`). `TestRebuildBeforeAcknowledgements` exports a store with no acknowledgement, removes `max_ack_id` from the state, rebuilds, and finds no acknowledgement, NULL `ack_changes` and the sequence starting at 1. An acknowledgement the sweep deleted comes back from older hours' files on a rebuild; the next sweep deletes it again.
- **The sweep's end of an episode.** An acknowledgement goes when it was ended before the window, when its finding is gone, when its finding resolved in the same episode before the window, or when the finding fires in a later episode that began before the window. The last is an upper bound on when the old episode ended (its resolve may already be swept), so an acknowledgement can stay one episode longer, never go early.
- **The episode's end writes nothing.** A resolve or a new episode does not set `ended_at`; the acknowledgement stops matching when findings are read, and `end_reason` is only `released` or `replaced`. `EndAcknowledgement` of one whose episode is over is failed_precondition, as of one already ended.
- **The messages are in a new file, `proto/natslens/v1/acknowledgements.proto`** (`Acknowledgement`, the two requests and responses), imported by `findings.proto` and `service.proto`; the RPCs are in `service.proto`. Field numbers as planned: `Finding.acknowledgement = 20`, `FindingTally.acknowledged = 7`.
- **The request.** Exactly one of `quiet_for` and `until_resolved`; `quiet_for` is truncated to whole seconds; the note is trimmed and may be empty.
- **`quiet` is read at the time the acknowledgement was chosen for**: now, or a past range's end, where the finding carries the acknowledgement in force then. `/metrics` reads at now.
- **A resolve ends an acknowledgement, even for a blip.** A finding that resolves for one collection and fires again starts a new episode, which the old acknowledgement does not cover; a flapping finding needs a new acknowledgement after each resolve.
- **Replacing gives no conflict signal.** A new acknowledgement ends the one before it whoever made that one, and nothing warns the person replaced; T3 shows the replaced one as "replaced by X" (its `ended_by`) so the team sees who took over.
- **The tally's `acknowledged` counts muted findings too**, as `flapping` does.
- **The event.** Stored with the summary "<code> acknowledged by alice@example.com: <note>" and `raw.detail` "acknowledged by alice@example.com: <note>"; the API words it "<entity>: acknowledged by …" as it words transitions. It reaches the API as an event with a `transition` whose state is unspecified (it carries the finding, the severity and the detail), so the UI shows no badge for it yet. The timeline's finding lane takes `finding.acknowledged` beside the transitions.
- **Metrics.** `nats_lens_finding_acknowledged` is written only while the quiet holds (value 1) and is absent otherwise, which is what the `unless on(...)` rule needs; `nats_lens_findings_acknowledged` counts the firing findings whose quiet holds, muted or not, every entity counted. Both are in `storeprov/metrics.go`; `internal/api/metrics.go` (the time series list) needed no change.
- **The demo writes no `finding.acknowledged` event**: adding one to a scenario's event list renumbers its event IDs, which the demo's tests and links pin. example-global's acknowledgement is on `consumer-002` for `label-printer` on `shipping-updates`: bob@example.com's, replaced by carol@example.com's, whose 30 minutes of quiet are over. An acknowledgement made through the API in live mode stays on its finding as the scenario moves: the episode is kept in the fixed frame.
- **One conformance row writes**: "an acknowledgement handed back does not show on its finding" acknowledges a finding without one and hands it back.

## T2 `GetOnCall`: one call for the phone card

A person on call opens the link on a phone, often on a slow network; one call gives the card everything, instead of the five the finding page makes today (`GetFinding`, `GetLensInfo`, `ListFindings`, `ListEvents`, `GetStream` or `GetConsumer`).

- **RPC.** `proto/natslens/v1/oncall.proto`, `GetOnCall(GetOnCallRequest) returns (GetOnCallResponse)`, read-only. Request: `system`, `finding_id`. Response: `Finding finding` (with its mute and acknowledgement), `repeated FindingTransition transitions` (the episode's), `int32 same_check_firing`, `repeated OnCallAsset assets` (at most 10) with `int32 assets_total`, `OnCallNow now`, `repeated ReplayStep steps` (Replay's message, at most 12) with `int32 steps_total` and `string steps_note`, `google.protobuf.Timestamp story_a`, `story_b`, `TimeWindow context_window`, `string playbook_url`.
- `OnCallAsset`: `EntityRef entity`, `string finding_id`, `Severity severity`, `optional int32 replicas`, `optional int32 online`, `string leader`.
- `OnCallNow`: `epoch_at`, `optional int32 servers_expected`, `optional int32 servers_answering`, `TimeWindow open_window` (a Kubernetes window still open), `optional double delivered_per_second` (the affected consumers' sum, unset when none reports), `optional double stream_msgs_per_second`.
- **Rules** in `internal/api/oncall.go` (`OnCallFacts`, `FinishOnCall`: the window choice, the story's span and cut, the assets' order and cut), shared by the store (`storeprov/oncall.go`) and the demo (`fake/oncall.go`). The story calls the provider's own `Replay` facts for its A and B and `api.FinishReplay`, so the steps are Replay's, worded once. A finding that resolved has its story to its resolve and `now` as it stands; the card says so. The call has the usual 30 seconds; a story that cannot be read (the A older than retention) leaves `steps` empty with the reason in `steps_note`, and the rest is served.
- **Playbook.** After open question 3: `internal/checks/remediation.go` reads an entry as a string or as `{text, playbook}`; `checks.Check` gains `Playbook`; `GetOnCall` returns it. A `playbook` that is not an `https` URL stops the start.
- **Demo.** `example-prod`'s `consumer-010` gives the whole card: the node upgrade as context, the node upgrade's Replay steps, `analytics-aggregator` missing with its last holders, delivery of `order-archive`'s other consumers, and a playbook URL `https://runbooks.example.com/nats/durable-missing` in the demo's own remediation. `example-staging` gives a card whose `now` is not reported (its collector closed).
- **Conformance rows:** a card with a context window and one without; an asset with replicas online and one not reported; steps cut at 12 with the total; a resolved finding's card; both providers.
- **Tests.** `FinishOnCall` cases for each rule; the store read under a non-UTC `TZ`; the call's count of queries (one per kind of fact, never one per asset).

### Where T2 departed from this plan

The implementation's choices are proposed, not yet confirmed.

- `OnCallAsset.answering = 7` carries a server's answering state explicitly; replicas and online remain unset for server entities.
- Kubernetes windows have no explicit open flag. The present's window uses the existing 15-minute quiet-gap rule; its last observed event must fall within that gap. The returned end remains that observation, not a predicted end.
- Present facts require a collection within 3 collect intervals, matching Replay's reach. The closed staging collector therefore returns unset present facts. Observed zero remains set.
- Review fix (proposed, not yet confirmed): both rates require a leader counter in the selected recent collection. Only the latest contiguous leader/creation/counter run contributes, with at least 2 samples; resets start a run. Historical rate APIs keep their existing range semantics. The 2 batch rate queries preserve 7 fact queries for 1, 10, and 100 affected consumers.
- Delivery sums cover reporting consumers of the affected streams, including siblings of an absent consumer. The sum is only the observed contribution, not evidence that every consumer reports or delivers. A Kubernetes window records events, not proof of an active upgrade. Last holders stay in the finding's existing detail and Replay evidence rather than a second asset-history representation.
- A story that begins before the stored history also returns empty steps with an explanation, as one outside retention does. Context and present facts remain available.
- A resolved or muted finding with no firing, unmuted group keeps its own asset, with a headline firing count of zero.
- Playbook URLs also reject credentials and control characters. Plain-string remediation entries keep their existing append behavior.
- The capability doc and both index entries are updated here as AGENTS.md requires. T4 still owns the global design and README changes; T3 owns the UI.

### Where T3 departed from this plan

Each point was decided in the session that built T3: proposed, not yet confirmed.

- The acknowledgement response patches the current finding and on-call caches before refetch only when their captured firing episode still matches and the cache revision is unchanged, or when the returned acknowledgement is strictly newer than the existing one. An intervening resolve, new episode, release, or newer acknowledgement wins. The UI waits for a successful write before showing the receipt; a failed write never claims ownership. Invalidation is limited to the captured system.
- The section retains a replacement or hand-back receipt during the current visit to the same system, finding, and episode; resolving clears the receipt. The API has no acknowledgement-history list; a reload reads the current episode's acknowledgement, and Events retains acknowledgement events. No server contract was added in T3.
- Both label-route destinations retain the existing global-query provider's range, system, and account; label-routing and unknown parameters do not propagate. A missing label lookup replaces the route with the check's Findings list and passes the explanatory message as navigation state. A real `not_found` response and an empty finding response take this path; other failures keep their API error.
- The right-now sentence names reporting consumers and streams; the context names an observed Kubernetes window, not an active upgrade. This carries the corrected M2 semantics through the UI.
- The phone remediation separates the opening sentence from subsequent sentences without changing the check's wording or splitting inline code.
- The browser check tried T3 Preview first. Its snapshot step failed twice with `Preview snapshot failed: Preview automation snapshot timed out after 15000ms.` The check continued in an isolated agent-browser session. The demo listens only on the task's unused loopback port, 18483.
